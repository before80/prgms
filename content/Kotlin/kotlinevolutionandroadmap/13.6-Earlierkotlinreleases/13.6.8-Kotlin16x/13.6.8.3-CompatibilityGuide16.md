# 13.6.8.3 Kotlin 1.6.x 兼容性指南

_[保持语言的现代性](../../../13.3-KotlinEvolutionPrinciples/)_ 和 _[舒适的更新](../../../13.3-KotlinEvolutionPrinciples/)_ 是 Kotlin 语言设计中的基本原则。前者指出，阻碍语言演进的构造应该被移除；后者指出，这种移除应事先充分沟通，以便代码迁移尽可能顺畅。

虽然大多数语言变更已经通过其他渠道公布过（例如更新日志或编译器警告），但本文汇总了所有这些变更，为从 Kotlin 1.5 迁移到 Kotlin 1.6 提供完整参考。

## 基本术语 {#basic-terms}

本文介绍了以下几种兼容性：

- _源码级_：源码不兼容的变更会让原本能正常编译（无错误或警告）的代码不再能编译
- _二进制级_：如果互换两个二进制产物不会导致加载或链接错误，则称它们是二进制兼容的
- _行为级_：如果同一个程序在应用变更前后的行为不同，则该变更属于行为不兼容

请记住，这些定义仅针对纯 Kotlin。从其他语言（例如 Java）的视角来看 Kotlin 代码的兼容性不在本文讨论范围内。

## 语言 {#language}

### 默认让带有 enum、sealed 和 Boolean 主语的 when 语句完备 {#make-when-statements-with-enum-sealed-and-boolean-subjects-exhaustive-by-default}

> **Issue**：[KT-47709](https://youtrack.jetbrains.com/issue/KT-47709) **组件**：核心语言 **不兼容变更类型**：源码级 **简要说明**：Kotlin 1.6 会对带有 enum、sealed 或 Boolean 主语的 `when` 语句不完备的情况发出警告 **弃用周期**：- 1.6.0：当带有 enum、sealed 或 Boolean 主语的 `when` 语句不完备时引入警告（在渐进模式下报告错误）- 1.7.0：把该警告提升为错误

### 弃用 when 带主语中令人困惑的语法 {#deprecate-confusing-grammar-in-when-with-subject}

> **Issue**：[KT-48385](https://youtrack.jetbrains.com/issue/KT-48385) **组件**：核心语言 **不兼容变更类型**：源码级 **简要说明**：Kotlin 1.6 将弃用 `when` 条件表达式中若干令人困惑的语法构造 **弃用周期**：- 1.6.20：对受影响的表达式引入弃用警告 - 1.8.0：把该警告提升为错误 - >= 1.8：把某些已弃用的构造重新用于新的语言特性

### 禁止在伴生对象和嵌套对象的父构造器调用中访问类成员 {#prohibit-access-to-class-members-in-the-super-constructor-call-of-its-companion-and-nested-objects}

> **Issue**：[KT-25289](https://youtrack.jetbrains.com/issue/KT-25289) **组件**：核心语言 **不兼容变更类型**：源码级 **简要说明**：如果伴生对象和普通对象父构造器调用的实参的接收者引用了包含它的声明，Kotlin 1.6 将对该实参报告错误 **弃用周期**：- 1.5.20：对存在问题的实参引入警告 - 1.6.0：把该警告提升为错误，可以用 `-XXLanguage:-ProhibitSelfCallsInNestedObjects` 临时回退到 1.6 之前的行为

### 类型可空性增强的改进 {#type-nullability-enhancement-improvements}

> **Issue**：[KT-48623](https://youtrack.jetbrains.com/issue/KT-48623) **组件**：Kotlin/JVM **不兼容变更类型**：源码级 **简要说明**：Kotlin 1.7 将改变它加载和解释 Java 代码中类型可空性注解的方式 **弃用周期**：- 1.4.30：对更精确的类型可空性可能导致错误的情况引入警告 - 1.7.0：推断更精确的 Java 类型可空性，可以用 `-XXLanguage:-TypeEnhancementImprovementsInStrictMode` 临时回退到 1.7 之前的行为

### 防止不同数值类型之间的隐式强制转换 {#prevent-implicit-coercions-between-different-numeric-types}
