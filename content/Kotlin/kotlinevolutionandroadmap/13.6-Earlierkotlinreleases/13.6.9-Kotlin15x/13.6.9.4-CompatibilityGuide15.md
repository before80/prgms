# 13.6.9.4 Kotlin 1.5.x 兼容性指南

_[保持语言现代性](../../../13.3-KotlinEvolutionPrinciples/)_ 和 _[平滑升级](../../../13.3-KotlinEvolutionPrinciples/)_ 是 Kotlin 语言设计的基本原则。前者指出，阻碍语言演进的构造应当被移除；后者指出，这种移除应当事先充分沟通，以便代码迁移尽可能顺畅。

虽然大多数语言变更已经通过其他渠道公布（例如更新日志或编译器警告），本文仍然把它们全部汇总，为从 Kotlin 1.4 迁移到 Kotlin 1.5 提供完整参考。

## 基本术语 {#basic-terms}

本文介绍几种兼容性：

- _源码（source）_：源码不兼容的变更会让原本能正常编译（没有错误或警告）的代码无法再编译
- _二进制（binary）_：如果互换两个二进制构件不会导致加载或链接错误，就称它们是二进制兼容的
- _行为（behavioral）_：如果同一个程序在应用变更前后表现出不同行为，就称该变更是行为不兼容的

请记住，这些定义仅针对纯 Kotlin。从其他语言（例如 Java）的视角来看 Kotlin 代码的兼容性不在本文讨论范围内。

## 语言与标准库 {#language-and-stdlib}

### 禁止在签名多态调用中使用展开运算符 {#forbid-spread-operator-in-signature-polymorphic-calls}

> **问题**：[KT-35226](https://youtrack.jetbrains.com/issue/KT-35226) **组件**：核心语言 **不兼容变更类型**：源码 **简要说明**：Kotlin 1.5 将禁止在签名多态调用中使用展开运算符（*） **弃用周期**：- < 1.5：在调用处对存在问题的运算符引入警告 - >= 1.5：把该警告升级为错误，可以使用 `-XXLanguage:-ProhibitSpreadOnSignaturePolymorphicCall` 暂时回退到 1.5 之前的行为

### 禁止非抽象类包含从该类不可见的抽象成员（internal/包级私有） {#forbid-non-abstract-classes-containing-abstract-members-invisible-from-that-classes-internal-package-private}

### 禁止在 JVM 上把基于非具体化类型参数的数组用作具体化类型实参 {#forbid-using-array-based-on-non-reified-type-parameters-as-reified-type-arguments-on-jvm}

> **问题**：[KT-35224](https://youtrack.jetbrains.com/issue/KT-35224) **组件**：核心语言 **不兼容变更类型**：源码 **简要说明**：Kotlin 1.5 将禁止在带 SAM 转换的实参之后传入未展开的数组 **弃用周期**：- 1.3.70：对存在问题的调用引入警告 - >= 1.5：把该警告升级为错误，可以使用 `-XXLanguage:-ProhibitVarargAsArrayAfterSamArgument` 暂时回退到 1.5 之前的行为

### 支持以下划线命名的 catch 块参数的特殊语义 {#support-special-semantics-for-underscore-named-catch-block-parameters}

### 把 SAM 转换的实现策略从基于匿名类改为 invokedynamic {#change-implementation-strategy-of-sam-conversion-from-anonymous-class-based-to-invokedynamic}

> **问题**：[KT-44912](https://youtrack.jetbrains.com/issue/KT-44912) **组件**：Kotlin/JVM **不兼容变更类型**：行为 **简要说明**：从 Kotlin 1.5 起，SAM（单一抽象方法）转换的实现策略将从生成匿名类改为使用 `invokedynamic` JVM 指令 **弃用周期**：- 1.5：改变 SAM 转换的实现策略，可以使用 `-Xsam-conversions=class` 把实现方式还原为之前使用的方案

### 基于 JVM IR 的后端的性能问题 {#performance-issues-with-the-jvm-ir-based-backend}

> **问题**：[KT-48233](https://youtrack.jetbrains.com/issue/KT-48233) **组件**：Kotlin/JVM **不兼容变更类型**：行为 **简要说明**：Kotlin 1.5 默认对 Kotlin/JVM 编译器使用[基于 IR 的后端](https://blog.jetbrains.com/kotlin/2021/02/the-jvm-backend-is-in-beta-let-s-make-it-stable-together/)。对于较早的语言版本，默认仍使用旧后端。在 Kotlin 1.5 中使用新编译器时，你可能会遇到一些性能下降问题。我们正在努力修复这些情况。 **弃用周期**：- < 1.5：默认使用旧的 JVM 后端 - >= 1.5：默认使用基于 IR 的后端。如果你需要在 Kotlin 1.5 中使用旧后端，请在项目的配置文件中加入以下内容，以暂时回退到 1.5 之前的行为：在 Gradle 中： ```kotlin tasks.withType<org.jetbrains.kotlin.gradle.dsl.KotlinJvmCompile> { kotlinOptions.useOldBackend = true } ``` ```groovy tasks.withType(org.jetbrains.kotlin.gradle.dsl.KotlinJvmCompile) { kotlinOptions.useOldBackend = true } ``` 在 Maven 中： ```xml <configuration> <args> <arg>-Xuse-old-backend</arg> </args> </configuration> ``` 对该标志的支持将在未来的某个版本中移除。

### 基于 JVM IR 的后端中新的字段排序 {#new-field-sorting-in-the-jvm-ir-based-backend}

> **问题**：[KT-46378](https://youtrack.jetbrains.com/issue/KT-46378) **组件**：Kotlin/JVM **不兼容变更类型**：行为 **简要说明**：从 1.5 版起，Kotlin 使用[基于 IR 的后端](https://blog.jetbrains.com/kotlin/2021/02/the-jvm-backend-is-in-beta-let-s-make-it-stable-together/)，它对 JVM 字节码的排序方式不同：它把在构造函数中声明的字段排在在类体中声明的字段之前，而旧后端则相反。新的排序可能改变那些依赖字段顺序的序列化框架（例如 Java 序列化）所影响程序的行为。 **弃用周期**：- < 1.5：默认使用旧的 JVM 后端。它把在类体中声明的字段排在构造函数中声明的字段之前。- >= 1.5：默认使用新的基于 IR 的后端。在构造函数中声明的字段会被生成在类体中声明的字段之前。作为变通办法，你可以在 Kotlin 1.5 中暂时切换到旧后端。为此，请在项目的配置文件中加入以下内容：在 Gradle 中： ```kotlin tasks.withType<org.jetbrains.kotlin.gradle.dsl.KotlinJvmCompile> { kotlinOptions.useOldBackend = true } ``` ```groovy tasks.withType(org.jetbrains.kotlin.gradle.dsl.KotlinJvmCompile) { kotlinOptions.useOldBackend = true } ``` 在 Maven 中： ```xml <configuration> <args> <arg>-Xuse-old-backend</arg> </args> </configuration> ``` 对该标志的支持将在未来的某个版本中移除。

### 为委托表达式含泛型调用的委托属性生成可空性断言 {#generate-nullability-assertion-for-delegated-properties-with-a-generic-call-in-the-delegate-expression}

### 在带具名 vararg 的调用中使用正确的实参求值顺序 {#use-the-correct-order-of-arguments-execution-in-calls-with-named-vararg}

## 工具 {#tools}

### 不要在一个项目中混用多个 kotlin-test 的 JVM 变体 {#do-not-mix-several-jvm-variants-of-kotlin-test-in-a-single-project}

> **问题**：[KT-40225](https://youtrack.jetbrains.com/issue/KT-40225) **组件**：Gradle **不兼容变更类型**：行为 **简要说明**：如果其中一个变体是由传递依赖引入的，项目中可能同时存在多个相互排斥的、面向不同测试框架的 `kotlin-test` 变体。从 1.5.0 起，Gradle 将不再允许同时存在相互排斥的、面向不同测试框架的 `kotlin-test` 变体。 **弃用周期**：- < 1.5：允许同时存在多个相互排斥的、面向不同测试框架的 `kotlin-test` 变体 - >= 1.5：行为已改变，Gradle 会抛出类似"Cannot select module with conflict on capability..."的异常。可能的解决办法：* 使用与传递依赖所引入的相同 `kotlin-test` 变体及相应的测试框架。* 找到该依赖的另一个不会传递引入该 `kotlin-test` 变体的版本，这样你就可以使用自己想用的测试框架。* 找到该依赖的另一个会传递引入其他 `kotlin-test` 变体的版本，且该变体使用你想用的测试框架。* 排除被传递引入的测试框架。下面的例子演示如何排除 JUnit 4：```groovy configurations { testImplementation.get().exclude("org.jetbrains.kotlin", "kotlin-test-junit") } ``` 排除该测试框架后，请测试你的应用。如果它无法正常工作，请回滚排除相关的改动，改用与该库相同的测试框架，并排除你自己的测试框架。
