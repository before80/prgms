这和我们的单链表栈是完全一样的逻辑。为什么情况不同了。为什么。

答案其实就是本章的核心教训：`RefCell` 让一切都变得悲伤。到目前为止，`RefCell` 只是烦人。现在它们要变成噩梦了。

那么发生了什么？要理解这一点，我们需要回到 `borrow` 的定义：

```rust
fn borrow<'a>(&'a self) -> Ref<'a, T>
fn borrow_mut<'a>(&'a self) -> RefMut<'a, T>
```

在布局那一节我们说过：

> Rather than enforcing this statically, RefCell enforces them at runtime.
> If you break the rules, RefCell will just panic and crash the program.
> Why does it return these Ref and RefMut things? Well, they basically behave
> like `Rc`s but for borrowing. Also they keep the RefCell borrowed until they go out
> of scope. **We'll get to that later.**

现在就是"稍后"了。

`Ref` 和 `RefMut` 分别实现了 `Deref` 和 `DerefMut`。所以在大多数意图和目的上，它们的行为*完全*像 `&T` 和 `&mut T`。然而，由于这些 trait 的工作方式，返回的引用的生命周期与 `Ref` 绑定，而不是与实际的 `RefCell` 绑定。这意味着只要我们还持有那个引用，`Ref` 就必须一直存在。

这实际上对正确性是必要的。当 `Ref` 被 drop 时，它会告诉 `RefCell` 不再被借用了。所以如果我们*真的*设法让引用比 `Ref` 存活得更久，我们可能在还有引用存在时获得 `RefMut`，从而彻底破坏 Rust 的类型系统。

那么我们该怎么办？我们只想返回一个引用，但我们需要让这个 `Ref` 一直存在。可一旦我们从 `peek` 返回引用，函数就结束了，`Ref` 也会离开作用域。

😖

据我所知，我们在这里实际上完全无路可走。你无法那样完全封装 `RefCell` 的使用。

但是……如果我们放弃完全隐藏实现细节呢？如果我们返回 `Ref` 呢？

```rust
pub fn peek_front(&self) -> Option<Ref<T>> {
    self.head.as_ref().map(|node| {
        node.borrow()
    })
}
```

嗯……对了。我们有的是 `Ref<Node<T>>`，但我们想要 `Ref<T>`。我们可以放弃所有封装希望直接返回那个。我们也可以让事情更复杂，把 `Ref<Node<T>>` 包在一个新类型里，只暴露对 `&T` 的访问。

这两个选项都*有点*逊。

相反，我们要更深入。来点*乐子*。我们的乐子来源是*这货*：

```rust
map<U, F>(orig: Ref<'b, T>, f: F) -> Ref<'b, U>
    where F: FnOnce(&T) -> &U,
          U: ?Sized
```

> Make a new Ref for a component of the borrowed data.

没错：就像你可以对 `Option` 做 `map` 一样，你也可以对 `Ref` 做 `map`。

我敢肯定某处有人因为*单子*什么的很兴奋，但我不在乎那些。而且我不认为它是真正的单子，因为没有类似 `None` 的情况，不过跑题了。

它很酷，这就够了。*我需要这个*。

```rust
pub fn peek_front(&self) -> Option<Ref<T>> {
    self.head.as_ref().map(|node| {
        Ref::map(node.borrow(), |node| &node.elem)
    })
}
```

```text
> cargo build
```

噢耶

我们来确认一下这能工作，把栈的测试改一改。我们得处理 `Ref` 不能比较的问题。

```rust
#[test]
fn peek() {
    let mut list = List::new();
    assert!(list.peek_front().is_none());
    list.push_front(1); list.push_front(2); list.push_front(3);

    assert_eq!(&*list.peek_front().unwrap(), &3);
}
```
