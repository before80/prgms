# 8.11 远程开发提示和技巧

　　本文介绍每个 VS Code [远程开发](https://aka.ms/vscode-remote/download/extension)扩展的故障排除提示和技巧。每个扩展的设置和使用详情请参阅 [SSH](../8.2-SSH/)、[容器](https://code.visualstudio.com/docs/devcontainers/containers)和 [WSL](../8.6-WSL/) 文章。也可以尝试入门[教程](../8.3-SSHTutorial/)，快速在远程环境中运行。

　　GitHub Codespaces 的提示和问题请参阅 [GitHub Codespaces 文档](https://docs.github.com/github/developing-online-with-codespaces)。

## SSH 提示 {#ssh-tips}

　　SSH 强大灵活，但也增加设置复杂性。本节包含在不同环境中启动和运行 Remote - SSH 扩展的提示和技巧。

## 自定义 AI 聊天响应 {#customize-ai-chat-responses}

　　[自定义指令](../../ai-in-vs-code/customize-and-extend/2.4.4-Instructions/)可以描述常见指南或规则，使响应符合特定编码实践和技术栈。

　　可以使用自定义指令告诉 Copilot 所连接远程环境的更多信息（例如安装了哪些语言或工具链）。可以像本地一样使用 `copilot-instructions.md` 文件。使用 Dev Container 时还有[额外指令配置步骤](https://code.visualstudio.com/docs/devcontainers/tips-and-tricks#customize-ai-chat-responses)。

### 配置 $EDITOR 变量 {#configuring-the-editor-variable}

macOS/Linux 远程主机请将以下片段添加到 shell 配置文件（例如 `.bashrc` 或 `.zshrc`）：

```bash
if [ "$VSCODE_INJECTION" = "1" ]; then
    export EDITOR="code --wait" # 或使用 VS Code Insiders 时的 'code-insiders'
fi
```

Windows 主机对应的 PowerShell：

```powershell
if ($env:VSCODE_INJECTION -eq "1") {
    $env:EDITOR = "code --wait"  # 或 VS Code Insiders 的 'code-insiders'
}
```

　　现在运行使用 `$EDITOR` 变量的终端命令（例如 `git commit`）会在 VS Code 中打开文件，而不是默认终端编辑器（如 `vim` 或 `nano`）。

### 配置基于密钥的身份验证 {#configuring-key-based-authentication}

　　[SSH 公钥身份验证](https://www.ssh.com/ssh/public-key-authentication)是一种方便、高安全的身份验证方法，将本地“私钥”与关联 SSH 主机用户账户的“公钥”结合。本节介绍如何生成密钥并添加到主机。

> **提示**：Windows 的 PuTTY 不是[受支持客户端](#installing-a-supported-ssh-client)，但可以[转换 PuTTYGen 密钥](#reusing-a-key-generated-in-puttygen)。

### 快速开始：使用 SSH 密钥 {#quick-start-using-ssh-keys}

为远程主机设置 SSH 密钥身份验证。首先创建密钥对，然后将公钥复制到主机。

**创建本地 SSH 密钥对**

检查**本地**机器是否已有 SSH 密钥。macOS/Linux 通常位于 `~/.ssh/id_ed25519.pub`，Windows 位于用户配置文件夹 `.ssh` 目录（例如 `C:\Users\your-user\.ssh\id_ed25519.pub`）。

没有密钥时，在**本地**终端/PowerShell 运行：

```bash
ssh-keygen -t ed25519 -b 4096
```

> **提示**：没有 `ssh-keygen`？请安装[受支持的 SSH 客户端](#installing-a-supported-ssh-client)。

**限制私钥文件权限**

* macOS/Linux 运行以下 shell 命令，必要时替换私钥路径：

    ```bash
    chmod 400 ~/.ssh/id_ed25519
    ```

* Windows 在 PowerShell 中为用户授予显式读取权限：

    ```powershell
    icacls "privateKeyPath" /grant <username>:R
    ```

    然后在 Windows 资源管理器中导航到私钥文件，右键单击选择 **属性**。选择 **安全** 选项卡 > **高级** > **禁用继承** > **从此对象中删除所有继承的权限**。

**授权 macOS 或 Linux 机器连接**

在**本地终端**运行以下命令之一，替换用户名和主机名，将本地公钥复制到 SSH 主机。

* 连接 **macOS 或 Linux** SSH 主机：

    ```bash
    export USER_AT_HOST="your-user-name-on-host@hostname"
    export PUBKEYPATH="$HOME/.ssh/id_ed25519.pub"

    ssh-copy-id -i "$PUBKEYPATH" "$USER_AT_HOST"
    ```

* 连接 **Windows** SSH 主机：

  * 主机使用 OpenSSH Server 且用户[属于管理员组](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_server_configuration#authorizedkeysfile)：

    ```bash
    export USER_AT_HOST="your-user-name-on-host@hostname"
    export PUBKEYPATH="$HOME/.ssh/id_ed25519.pub"

    ssh $USER_AT_HOST "powershell Add-Content -Force -Path \"\$Env:PROGRAMDATA\\ssh\\administrators_authorized_keys\" -Value '$(tr -d '\n\r' < "$PUBKEYPATH")'"
    ```

  * 否则：

    ```bash
    export USER_AT_HOST="your-user-name-on-host@hostname"
    export PUBKEYPATH="$HOME/.ssh/id_ed25519.pub"

    ssh $USER_AT_HOST "powershell New-Item -Force -ItemType Directory -Path \"\$HOME\\.ssh\"; Add-Content -Force -Path \"\$HOME\\.ssh\\authorized_keys\" -Value '$(tr -d '\n\r' < "$PUBKEYPATH")'"
    ```

    建议验证 SSH 主机远程用户 `.ssh` 文件夹中的 `authorized_keys` 文件归你所有，其他用户无权访问。详情请参阅 [OpenSSH wiki](https://github.com/PowerShell/Win32-OpenSSH/wiki/Security-protection-of-various-files-in-Win32-OpenSSH#authorized_keys)。

**授权 Windows 机器连接**

在**本地 PowerShell** 运行以下命令之一，替换用户名和主机名：

* 连接 **macOS 或 Linux** SSH 主机：

    ```powershell
    $USER_AT_HOST="your-user-name-on-host@hostname"
    $PUBKEYPATH="$HOME\.ssh\id_ed25519.pub"

    $pubKey=(Get-Content "$PUBKEYPATH" | Out-String); ssh "$USER_AT_HOST" "mkdir -p ~/.ssh && chmod 700 ~/.ssh && echo '${pubKey}' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
    ```

* 连接 **Windows** SSH 主机：

  * 主机使用 OpenSSH Server 且用户[属于管理员组](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_server_configuration#authorizedkeysfile)：

    ```powershell
    $USER_AT_HOST="your-user-name-on-host@hostname"
    $PUBKEYPATH="$HOME\.ssh\id_ed25519.pub"

    Get-Content "$PUBKEYPATH" | Out-String | ssh $USER_AT_HOST "powershell `"Add-Content -Force -Path `"`$Env:PROGRAMDATA\ssh\administrators_authorized_keys`" `""
    ```

  * 否则：

    ```powershell
    $USER_AT_HOST="your-user-name-on-host@hostname"
    $PUBKEYPATH="$HOME\.ssh\id_ed25519.pub"

    Get-Content "$PUBKEYPATH" | Out-String | ssh $USER_AT_HOST "powershell `"New-Item -Force -ItemType Directory -Path `"`$HOME\.ssh`"; Add-Content -Force -Path `"`$HOME\.ssh\authorized_keys`" `""
    ```

    验证远程用户 `.ssh` 文件夹中的 `authorized_keys` 文件归你所有，其他用户无权访问。详情请参阅 [OpenSSH wiki](https://github.com/PowerShell/Win32-OpenSSH/wiki/Security-protection-of-various-files-in-Win32-OpenSSH#authorized_keys)。

### 使用专用密钥提高安全性 {#improving-your-security-with-a-dedicated-key}

　　在所有 SSH 主机使用同一密钥很方便，但任何人获取私钥后也能访问所有主机。可以为开发主机创建单独 SSH 密钥：

1. 在不同文件中生成单独 SSH 密钥。

    **macOS/Linux**：在**本地终端**运行：

    ```bash
    ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519-remote-ssh
    ```

    **Windows**：在**本地 PowerShell** 运行：

    ```powershell
    ssh-keygen -t ed25519 -f "$HOME\.ssh\id_ed25519-remote-ssh"
    ```

2. 按照[快速开始](#quick-start-using-ssh-keys)步骤在 SSH 主机授权密钥，但将 `PUBKEYPATH` 设置为 `id_ed25519-remote-ssh.pub`。

3. 在 VS Code 命令面板（`F1`）运行 **Remote-SSH: Open Configuration File...**，选择 SSH 配置文件，添加或修改主机条目：

    ```yaml
    Host name-of-ssh-host-here
        User your-user-name-on-host
        HostName host-fqdn-or-ip-goes-here
        IdentityFile ~/.ssh/id_ed25519-remote-ssh
    ```

    > **提示**：Windows 路径也可以使用 `/`。使用 `\` 时需要双斜杠，例如 `C:\\path\\to\\my\\id_ed25519`。

### 复用 PuTTYGen 生成的密钥 {#reusing-a-key-generated-in-puttygen}

　　使用 PuTTYGen 设置 SSH 公钥身份验证时，需要转换私钥以便其他 SSH 客户端使用：

1. 在**本地**打开 PuTTYGen 并加载要转换的私钥。
2. 从应用菜单选择 **Conversions > Export OpenSSH key**，将转换后的密钥保存到用户配置文件夹 `.ssh` 目录（例如 `C:\Users\youruser\.ssh`）。
3. 验证新**本地**文件归你所有，其他用户无权访问。
4. 在 VS Code 命令面板（`F1`）运行 **Remote-SSH: Open Configuration File...**，选择 SSH 配置文件，添加或修改主机条目指向该文件：

    ```yaml
    Host name-of-ssh-host-here
        User your-user-name-on-host
        HostName host-fqdn-or-ip-goes-here
        IdentityFile ~/.ssh/exported-keyfile-from-putty
    ```

### 提高多用户服务器上的安全性 {#improving-security-on-multi-user-servers}

　　Remote - SSH 扩展安装并维护“VS Code Server”。服务器使用随机生成的密钥启动，任何新连接都需要提供密钥。密钥存储在远程磁盘上，仅当前用户可读。有一个无需身份验证的 HTTP 路径 `/version`。

　　默认情况下，服务器监听 `localhost` 的随机 TCP 端口，然后转发到本地机器。连接 **Linux 或 macOS** 主机时，可以改用锁定到特定用户的 Unix 套接字，然后转发套接字而不是端口。

> **注意**：此设置**禁用连接多路复用**，建议配置[公钥身份验证](#configuring-key-based-authentication)。

配置：

1. 确保 Windows、macOS 或 Linux 上有**本地 OpenSSH 6.7+ SSH 客户端**，并有 **OpenSSH 6.7+ Linux 或 macOS 主机**（Windows 不支持此模式）。
2. 在**本地** VS Code [用户设置](../../editor/3.3-ConfigureTheEditor/3.3.4-Settings/)中启用 **Remote.SSH: Remote Server Listen On Socket**，切换到套接字模式。

    ![监听套接字 VS Code 设置](../images/ssh-listen-on-socket.png)

3. 已连接 SSH 主机时，从命令面板（`F1`）选择 **Remote-SSH: Kill VS Code Server on Host...**，使设置生效。

连接出错时，可能需要在 SSH 主机 [sshd 配置](https://www.ssh.com/ssh/sshd_config/)启用套接字转发：

1. 在 **SSH 主机**（不是本地）使用文本编辑器（vi、nano 或 pico）打开 `/etc/ssh/sshd_config`。
2. 添加 `AllowStreamLocalForwarding yes`。
3. 重启 SSH 服务器（Ubuntu 上运行 `sudo systemctl restart sshd`）。
4. 重试。

### 排查连接挂起或失败 {#troubleshooting-hanging-or-failing-connections}

　　连接时 VS Code 挂起（可能超时）可以尝试以下方法。

**常规故障排除：移除服务器**

　　**Remote-SSH: Kill VS Code Server on Host** 命令可解决多种 Remote-SSH 问题并移除服务器，例如“Could not establish connection to `server_name`: The VS Code Server failed to start.”。

**检查 VS Code 是否在等待提示**

　　启用 `remote.SSH.showLoginTerminal` [设置](../../editor/3.3-ConfigureTheEditor/3.3.4-Settings/)并重试。提示输入密码或令牌时，请参阅[启用备用 SSH 身份验证方法](#enabling-alternate-ssh-authentication-methods)减少提示频率。

仍然有问题时，在 `settings.json` 设置以下属性并重试：

```json
"remote.SSH.showLoginTerminal": true,
"remote.SSH.useLocalServer": false
```

**绕过某些 Windows OpenSSH 服务器版本的缺陷**

　　某些 OpenSSH Server for Windows 版本存在缺陷，默认检查可能无法正确判断主机是否运行 Windows。Windows 1909 及以下自带 OpenSSH Server 不受影响。

可以在 `settings.json` 中告诉 VS Code SSH 主机运行 Windows：

```json
"remote.SSH.useLocalServer": false
```

也可以强制将特定主机标识为 Windows：

```json
"remote.SSH.remotePlatform": {
    "host-in-ssh-config-or-fqdn": "windows"
}
```

　　服务器版本高于 8.1.0.0 时此问题已修复。

**在远程主机启用 TCP 转发**

Remote - SSH 使用 SSH 隧道与主机通信，某些 SSH 服务器可能禁用。打开输出窗口 **Remote - SSH** 类别，检查：

```
open failed: administratively prohibited: open failed
```

　　看到此消息时，更新 SSH 服务器 [sshd 配置](https://www.ssh.com/ssh/sshd_config/)：

1. 在 **SSH 主机**（不是本地）使用文本编辑器打开 `/etc/ssh/sshd_config` 或 `C:\ProgramData\ssh\sshd_config`。
2. 添加 `AllowTcpForwarding yes`。
3. 重启 SSH 服务器（Ubuntu 上 `sudo systemctl restart sshd`，Windows 管理员 PowerShell 中 `Restart-Service sshd`）。
4. 重试。

**在 SSH 配置文件中设置 ProxyCommand**

　　位于代理后且无法连接 SSH 主机时，可能需要在**本地** [SSH 配置文件](https://linux.die.net/man/5/ssh_config)中为主机使用 `ProxyCommand`。示例请参阅 [SSH ProxyCommand 文章](https://www.cyberciti.biz/faq/linux-unix-ssh-proxycommand-passing-through-one-host-gateway-server/)。

**确保远程机器可以访问 Internet**

　　远程机器必须能访问 Internet，才能从 Marketplace 下载 VS Code Server 和扩展。连接要求请参阅[常见问题](../8.12-FAQ/)。

**在远程主机设置 HTTP_PROXY / HTTPS_PROXY**

　　远程主机位于代理后时，可能需要在 **SSH 主机**设置 HTTP_PROXY 或 HTTPS_PROXY 环境变量。打开 `~/.bashrc` 添加（将 `proxy.fqdn.or.ip:3128` 替换为正确主机名/IP 和端口）：

```bash
export HTTP_PROXY=http://proxy.fqdn.or.ip:3128
export HTTPS_PROXY=$HTTP_PROXY

# 或需要身份验证的代理
export HTTP_PROXY=http://username:password@proxy.fqdn.or.ip:3128
export HTTPS_PROXY=$HTTP_PROXY
```

**绕过以 `noexec` 挂载的 `/tmp`**

　　某些远程服务器禁止从 `/tmp` 执行脚本。VS Code 将安装脚本写入系统临时目录并尝试执行。请与系统管理员确认是否可以绕过。

**检查安装期间是否启动了不同 shell**

　　某些用户在 **SSH 主机** `.bash_profile` 或其他启动脚本中启动不同 shell。这会破坏 VS Code 远程服务器安装脚本，不建议这样做。请使用 `chsh` 更改远程机器默认 shell。

**连接动态分配机器的系统**

　　某些系统每次 SSH 连接都会动态路由到集群中的一个节点。VS Code 打开远程窗口会建立两个连接：第一个安装或启动 VS Code Server（或查找已运行实例），第二个创建 SSH 端口隧道。第二个连接路由到不同机器时，VS Code 无法与服务器通信。

　　OpenSSH 的 `ControlMaster` 选项（仅 macOS/Linux 客户端）可以将两个连接多路复用到同一节点的单个 SSH 连接。请参阅[启用备用 SSH 身份验证方法](#enabling-alternate-ssh-authentication-methods)。

**联系系统管理员获取配置帮助**

　　SSH 协议灵活，支持多种配置。登录终端或 **Remote-SSH** 输出窗口出现其他错误时，可能是缺少设置。

　　请系统管理员提供 SSH 主机和客户端所需设置。可以在 [SSH 配置文件](https://linux.die.net/man/5/ssh_config)中添加特定命令行参数。

在命令面板（`F1`）运行 **Remote-SSH: Open Configuration File...** 访问配置文件，然后与管理员合作添加必要设置。
### 启用备用 SSH 身份验证方法 {#enabling-alternate-ssh-authentication-methods}

　　连接 SSH 远程主机时，如果：

* 使用双重身份验证
* 使用密码身份验证
* 使用带密码短语的 SSH 密钥，且 [SSH 代理](#setting-up-the-ssh-agent)未运行或不可访问

　　VS Code 应自动提示输入所需信息。看不到提示时，请启用 `remote.SSH.showLoginTerminal` [设置](../../editor/3.3-ConfigureTheEditor/3.3.4-Settings/)。此设置会在 VS Code 运行 SSH 命令时显示终端。终端出现时输入身份验证代码、密码或密码短语。

仍然有问题时，在 `settings.json` 中添加以下属性并重试：

```json
"remote.SSH.showLoginTerminal": true,
"remote.SSH.useLocalServer": false
```

　　macOS 和 Linux 上想减少输入密码或令牌的次数，可以在**本地机器**启用 `ControlMaster`，让 OpenSSH 在单个连接上运行多个 SSH 会话。

启用 `ControlMaster`：

1. 在 SSH 配置文件中添加：

    ```yaml
    Host *
        ControlMaster auto
        ControlPath  ~/.ssh/sockets/%r@%h-%p
        ControlPersist  600
    ```

2. 运行 `mkdir -p ~/.ssh/sockets` 创建套接字文件夹。

### 设置 SSH 代理 {#setting-up-the-ssh-agent}

　　使用带密码短语的密钥连接 SSH 主机时，请确保 [SSH 代理](https://www.ssh.com/ssh/agent)在**本地**运行。VS Code 会自动将密钥添加到代理，因此每次打开远程窗口时无需输入密码短语。

要验证代理正在运行且可从 VS Code 环境访问，请在本地 VS Code 窗口终端运行 `ssh-add -l`。应该看到代理中的密钥列表（或没有密钥的消息）。代理未运行时，请按以下说明启动。启动后请重启 VS Code。

**Windows：**

要在 Windows 自动启用 SSH 代理，请启动**本地管理员 PowerShell** 并运行：

```powershell
# 确保以管理员身份运行
Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent
Get-Service ssh-agent
```

现在登录时代理会自动启动。

**Linux：**

后台启动 SSH 代理：

```bash
eval "$(ssh-agent -s)"
```

要在登录时自动启动，请将以下行添加到 `~/.bash_profile`：

```bash
if [ -z "$SSH_AUTH_SOCK" ]; then
   # 检查是否已有代理实例运行
   RUNNING_AGENT="`ps -ax | grep 'ssh-agent -s' | grep -v grep | wc -l | tr -d '[:space:]'`"
   if [ "$RUNNING_AGENT" = "0" ]; then
        # 启动新代理实例
        ssh-agent -s &> .ssh/ssh-agent
   fi
   eval `cat .ssh/ssh-agent`
fi
```

**macOS：**

macOS 上代理默认运行。

### 让本地 SSH 代理在远程可用 {#making-local-ssh-agent-available-on-the-remote}

　　本地 SSH 代理让 Remote - SSH 扩展无需反复输入密码短语即可连接远程系统，但远程运行的 Git 等工具无法访问本地解锁的私钥。

　　在远程集成终端运行 `ssh-add -l` 可以看到此问题：命令应列出已解锁密钥，却报告无法连接身份验证代理。设置 `ForwardAgent yes` 可以让本地 SSH 代理在远程环境可用。

编辑 `.ssh/config`（或 `Remote.SSH.configFile` 指向的文件，使用 **Remote-SSH: Open SSH Configuration File...** 命令确认），添加：

```ssh-config
Host *
    ForwardAgent yes
```

　　注意可以更严格地只为特定命名主机设置该选项。

### 修复 SSH 文件权限错误 {#fixing-ssh-file-permission-errors}

　　SSH 对文件权限很严格，设置不正确时可能看到“WARNING: UNPROTECTED PRIVATE KEY FILE!”等错误。以下各节介绍如何修复文件权限。

### 本地 SSH 文件和文件夹权限 {#local-ssh-file-and-folder-permissions}

**macOS / Linux：**

本地机器确保设置以下权限：

| 文件夹 / 文件 | 权限 |
|---------------|---------------------------|
| 用户文件夹中的 `.ssh` | `chmod 700 ~/.ssh` |
| 用户文件夹中的 `.ssh/config` | `chmod 600 ~/.ssh/config` |
| 用户文件夹中的 `.ssh/id_ed25519.pub` | `chmod 600 ~/.ssh/id_ed25519.pub` |
| 任何其他密钥文件 | `chmod 600 /path/to/key/file` |

**Windows：**

　　预期权限因 SSH 实现而异。建议使用开箱即用的 [Windows 10 OpenSSH 客户端](https://learn.microsoft.com/windows-server/administration/openssh/openssh_overview)。

此时确保 SSH 主机远程用户 `.ssh` 文件夹中的所有文件归你所有，其他用户无权访问。详情请参阅 [Windows OpenSSH wiki](https://github.com/PowerShell/Win32-OpenSSH/wiki/Security-protection-of-various-files-in-Win32-OpenSSH)。

其他客户端请查阅其文档了解预期权限。

### 服务器 SSH 文件和文件夹权限 {#server-ssh-file-and-folder-permissions}

**macOS / Linux：**

远程机器确保设置以下权限：

| 文件夹 / 文件 | Linux / macOS 权限 |
|---------------|---------------------------|
| 服务器用户文件夹中的 `.ssh` | `chmod 700 ~/.ssh` |
| 服务器用户文件夹中的 `.ssh/authorized_keys` | `chmod 600 ~/.ssh/authorized_keys` |

注意目前仅支持 Linux 主机，因此省略 macOS 和 Windows 10 权限。

**Windows：**

　　Windows OpenSSH 服务器文件权限请参阅 [Windows OpenSSH wiki](https://github.com/PowerShell/Win32-OpenSSH/wiki/Security-protection-of-various-files-in-Win32-OpenSSH)。

### 使用 SSHFS 访问远程主机上的文件 {#using-sshfs-to-access-files-on-your-remote-host}

　　[SSHFS](https://en.wikipedia.org/wiki/SSHFS) 是基于 SFTP 的安全远程文件系统访问协议。与 CIFS/Samba 共享相比，它只需要 SSH 访问机器。

> **注意**：出于性能原因，SSHFS 最适合单文件编辑和上传/下载内容。需要批量读写许多文件的应用（例如本地源代码管理工具）请使用 [rsync](#using-rsync-to-maintain-a-local-copy-of-your-source-code)。

**macOS / Linux**：

　　Linux 上可以使用发行版包管理器安装 SSHFS。Debian/Ubuntu：`sudo apt-get install sshfs`

> **注意**：WSL 1 不支持 FUSE 或 SSHFS，因此 Windows 当前说明不同。**WSL 2 包含 FUSE 和 SSHFS 支持**。

macOS 上可以使用 [Homebrew](https://brew.sh/) 安装：

```bash
brew install --cask macfuse
brew install gromgit/fuse/sshfs-mac
brew link --overwrite sshfs-mac
```

　　如果不想使用命令行挂载远程文件系统，也可以安装 [SSHFS GUI](https://github.com/dstuecken/sshfs-gui)。

命令行使用方法：在本地终端运行以下命令（将 `user@hostname` 替换为远程用户名和主机名/IP）：

```bash
export USER_AT_HOST=user@hostname
# 创建挂载远程文件系统的目录
mkdir -p "$HOME/sshfs/$USER_AT_HOST"
# 挂载远程文件系统
sshfs "$USER_AT_HOST:" "$HOME/sshfs/$USER_AT_HOST" -ovolname="$USER_AT_HOST" -p 22  \
    -o workaround=nonodelay -o transform_symlinks -o idmap=user  -C
```

　　这会将远程机器主文件夹挂载到 `~/sshfs`。完成后可以使用操作系统 Finder/文件资源管理器或命令行卸载：

```bash
umount "$HOME/sshfs/$USER_AT_HOST"
```

**Windows：**

按以下步骤操作：

1. 在 Linux 上向项目添加 `.gitattributes` 文件，**强制 Linux 和 Windows 之间一致的行尾**，避免 CRLF/LF 差异导致意外问题。详情请参阅[解决 Git 行尾问题](#resolving-git-line-ending-issues-in-wsl-resulting-in-many-modified-files)。

2. 使用 [Chocolatey](https://chocolatey.org/) 安装 [SSHFS-Win](https://github.com/billziss-gh/sshfs-win)：`choco install sshfs`

3. 安装后可以使用文件资源管理器的 **映射网络驱动器...** 选项，路径为 `\\sshfs\user@hostname`，其中 `user@hostname` 是远程用户名和主机名/IP。可以在命令提示符中脚本化：`net use /PERSISTENT:NO X: \\sshfs\user@hostname`

4. 完成后在文件资源管理器中右键单击驱动器，选择 **断开连接**。

### 从终端连接到远程主机 {#connect-to-a-remote-host-from-the-terminal}

　　配置主机后，可以通过传递远程 URI 从终端直接连接。

例如，连接 `remote_server` 并打开 `/code/my_project` 文件夹：

```bash
code --remote ssh-remote+remote_server /code/my_project
```

　　需要猜测输入路径是文件还是文件夹。有文件扩展名时视为文件。

要强制打开文件夹，请在路径末尾添加斜杠或使用：

`code --folder-uri vscode-remote://ssh-remote+remote_server/code/folder.with.dot`

要强制打开文件，请添加 `--goto` 或使用：

`code --file-uri vscode-remote://ssh-remote+remote_server/code/fileWithoutExtension`

### 使用 rsync 维护源代码的本地副本 {#using-rsync-to-maintain-a-local-copy-of-your-source-code}

　　[使用 SSHFS 访问远程文件](#using-sshfs-to-access-files-on-your-remote-host)的替代方案是使用 [`rsync`](https://rsync.samba.org/) 将远程主机文件夹全部内容复制到本地机器。`rsync` 每次运行会确定需要更新的文件，比 `scp` 或 `sftp` 更高效方便。确实需要使用多文件或性能密集型本地工具时可以考虑。

　　`rsync` 在 macOS 上开箱可用，Linux 可以通过包管理器安装（例如 Debian/Ubuntu 上 `sudo apt-get install rsync`）。Windows 需要使用 [WSL](https://learn.microsoft.com/windows/wsl/install) 或 [Cygwin](https://www.cygwin.com/)。

使用方法：导航到要存储同步内容的文件夹，运行以下命令，将 `user@hostname` 替换为远程用户名和主机名/IP，`/remote/source/code/path` 替换为远程源代码位置。

**macOS、Linux 或 WSL 内**：

```bash
rsync -rlptzv --progress --delete --exclude=.git "user@hostname:/remote/source/code/path" .
```

或从 Windows PowerShell 使用 **WSL**：

```powershell
wsl rsync -rlptzv --progress --delete --exclude=.git "user@hostname:/remote/source/code/path" "`$(wslpath -a '$PWD')"
```

　　每次需要最新文件副本时重新运行，只传输更新。`.git` 文件夹有意排除，既为性能，也便于使用本地 Git 工具而不受远程主机状态影响。

要推送内容，请反转源和目标参数。但 **Windows 上**应先向项目添加 `.gitattributes` 文件**强制一致行尾**。详情请参阅[解决 Git 行尾问题](#resolving-git-line-ending-issues-in-wsl-resulting-in-many-modified-files)。

```bash
rsync -rlptzv --progress --delete --exclude=.git . "user@hostname:/remote/source/code/path"
```

### 清理远程主机上的 VS Code Server {#cleaning-up-the-vs-code-server-on-the-remote}

　　SSH 扩展提供从远程机器清理 VS Code Server 的命令 **Remote-SSH: Uninstall VS Code Server from Host...**。该命令会终止所有运行中的 VS Code Server 进程，并删除服务器安装文件夹。

　　需要手动执行或命令不工作时，可以运行：

```bash
# 终止服务器进程
kill -9 $(ps aux | grep vscode-server | grep $USER | grep -v grep | awk '{print $2}')
# 删除相关文件和文件夹
rm -rf $HOME/.vscode-server # 或 ~/.vscode-server-insiders
```

　　VS Code Server 以前安装在 `~/.vscode-remote` 下，也可以检查该位置。

## WSL 提示 {#wsl-tips}

### 首次启动：VS Code Server 前提条件 {#first-time-start-vs-code-server-prerequisites}

　　某些 WSL Linux 发行版缺少 VS Code 服务器启动所需库，可以使用包管理器添加。

#### Debian 和 Ubuntu {#debian-and-ubuntu}

打开 Debian 或 Ubuntu WSL shell，添加 `wget` 和 `ca-certificates`：

```sh
sudo apt-get update && sudo apt-get install wget ca-certificates
```

#### Alpine {#alpine}

以 root 打开 Alpine WSL shell（`wsl -d Alpine -u root`），添加 `libstdc++`：

```sh
apk update && apk add libstdc++
```

Windows 10 April 2018 Update（build 1803）及更早版本还需要 `/bin/bash`：

```sh
apk update && apk add bash
```

### 选择 WSL 扩展使用的发行版 {#selecting-the-distribution-used-by-the-wsl-extension}

　　**WSL: New Window** 会打开注册为默认的 WSL 发行版。

要打开非默认发行版，请从该发行版的 WSL shell 运行 `code .`，或使用 **WSL: New Window using Distro**。

　　Windows 10 May 2019 Update（1903）之前的 WSL 版本中，WSL 命令只能使用**默认发行版**。因此 WSL 扩展可能提示是否同意更改默认发行版。

始终可以使用 [wslconfig.exe](https://learn.microsoft.com/windows/wsl/wsl-config) 更改默认值，例如：

```bat
wslconfig /setdefault Ubuntu
```
可以运行以下命令查看已安装的发行版：

```bat
wslconfig /l
```

### 配置服务器启动环境 {#configure-the-environment-for-the-server-startup}

　　WSL 扩展在 WSL 中启动 VS Code 服务器时不运行任何 shell 配置脚本，以避免自定义配置脚本阻止启动。

　　需要配置启动环境时，可以使用[高级环境设置脚本](../8.6-WSL/)。

### 配置远程扩展宿主环境 {#configure-the-environment-for-the-remote-extension-host}

　　远程扩展宿主和终端环境基于默认 shell 的配置脚本。为求值远程扩展宿主进程的环境变量，服务器会以**交互式登录 shell** 创建默认 shell 实例，探测其环境变量并将其作为远程扩展宿主进程的初始环境。因此环境变量值取决于配置的默认 shell 及其配置脚本内容。

　　各 shell 配置脚本概览请参阅 [Unix shell 初始化](https://github.com/rbenv/rbenv/wiki/unix-shell-initialization)。大多数 WSL 发行版默认 shell 为 `/bin/bash`。`/bin/bash` 会先查找 `/etc/profile`，然后查找 `~/.bash_profile`、`~/.bash_login`、`~/.profile`。

　　要更改 WSL 发行版默认 shell，请遵循[此博客文章](https://medium.com/@vinhp/set-and-use-zsh-as-default-shell-in-wsl-on-windows-10-the-right-way-4f30ed9592dc)的说明。

### 修复 code 命令不工作的问题 {#fixing-problems-with-the-code-command-not-working}

　　在 Windows 的 WSL 终端输入 `code` 时因找不到命令而无法工作，可能 WSL PATH 缺少关键位置。

打开 WSL 终端并输入 `echo $PATH` 检查。应看到 VS Code 安装路径。默认位置为：

```bash
/mnt/c/Users/Your Username/AppData/Local/Programs/Microsoft VS Code/bin
```

使用**系统安装程序**时，安装路径为：

```bash
/mnt/c/Program Files/Microsoft VS Code/bin
```

或：

```bash
/mnt/c/Program Files (x86)/Microsoft VS Code/bin
```

　　WSL 会从 Windows PATH 变量继承路径。要更改 Windows PATH，请从 Windows 开始菜单使用 **编辑账户的环境变量** 命令。

禁用路径共享时，请编辑 `.bashrc`，添加以下内容并启动新终端：

```bash
WINDOWS_USERNAME="Your Windows Alias"

export PATH="$PATH:/mnt/c/Windows/System32:/mnt/c/Users/${WINDOWS_USERNAME}/AppData/Local/Programs/Microsoft VS Code/bin"
# 或...
# export PATH="$PATH:/mnt/c/Program Files/Microsoft VS Code/bin"
# 或...
# export PATH="$PATH:/mnt/c/Program Files (x86)/Microsoft VS Code/bin"

```

> **注意**：请确保引用或转义目录名中的空格。

### 服务器因段错误启动失败 {#the-server-fails-to-start-with-a-segmentation-fault}

　　可以通过发送核心转储文件帮助调查此问题。获取核心转储文件：

在 Windows 命令提示符中：

* 运行 `code --locate-extension ms-vscode-remote.remote-wsl` 确定 WSL 扩展文件夹。

### 重命名文件夹时出现 EACCES: permission denied 错误 {#i-see-eacces-permission-denied-error-trying-to-rename-a-folder-in-the-open-workspace}

　　这是 WSL 文件系统实现的已知问题（[Microsoft/WSL#3395](https://github.com/microsoft/WSL/issues/3395)、[Microsoft/WSL#1956](https://github.com/microsoft/WSL/issues/1956)），由 VS Code 的活动文件监视器引起。该问题仅在 WSL 2 中修复。

避免此问题，请将 `remote.WSL.fileWatcher.polling` 设置为 true。但轮询会对大型工作区产生性能影响。

大型工作区可以增大轮询间隔 `remote.WSL.fileWatcher.pollingInterval`，并使用 `files.watcherExclude` 控制监视的文件夹。

　　[WSL 2](https://learn.microsoft.com/windows/wsl/compare-versions#whats-new-in-wsl-2) 没有此文件监视器问题，不受新设置影响。

### 解决 WSL 中的 Git 行尾问题 {#resolving-git-line-ending-issues-in-wsl-resulting-in-many-modified-files}

　　Windows 和 Linux 默认行尾不同，Git 可能报告大量仅行尾不同的已修改文件。可以通过 `.gitattributes` 文件或 Windows 全局设置禁用行尾转换。

　　在仓库中添加或修改 `.gitattributes` 通常是最可靠的方法。提交到源代码管理有助于他人，并可按仓库调整行为。例如，在仓库根目录 `.gitattributes` 中添加以下内容，强制所有文件使用 LF，但需要 CRLF 的 Windows 批处理文件除外：

```yaml
* text=auto eol=lf
*.{cmd,[cC][mM][dD]} text eol=crlf
*.{bat,[bB][aA][tT]} text eol=crlf
```

　　这适用于 **Git v2.10+**，遇到问题时请确保安装较新的 Git 客户端。可以在此文件中添加其他需要 CRLF 的文件类型。

如果仍希望始终上传 Unix 风格行尾（LF），可以使用 `input` 选项：

```bash
git config --global core.autocrlf input
```

如果希望完全禁用行尾转换，请运行：

```bash
git config --global core.autocrlf false
```

最后，可能需要重新克隆仓库才能使这些设置生效。

### 在 Windows 和 WSL 之间共享 Git 凭据 {#sharing-git-credentials-between-windows-and-wsl}

　　使用 HTTPS 克隆仓库且**在 Windows 配置了[凭据帮助程序](https://docs.github.com/get-started/getting-started-with-git/caching-your-github-credentials-in-git)** 时，可以与 WSL 共享，使两侧保存输入的密码（不适用于 SSH 密钥）。

按以下步骤操作：

1. 在 **Windows 命令提示符**或 **PowerShell** 中运行以下命令配置 Windows 凭据管理器：

    ```bat
     git config --global credential.helper wincred
    ```

2. 在 **WSL 终端**中运行以下命令，配置 WSL 使用相同凭据帮助程序：

    ```bash
     git config --global credential.helper "/mnt/c/Program\ Files/Git/mingw64/bin/git-credential-manager.exe"
    ```

　　Windows 侧使用 Git 时输入的密码现在可供 WSL 使用，反之亦然。

### 解决 WSL 中 Git 推送或同步挂起 {#resolving-hangs-when-doing-a-git-push-or-sync-from-wsl}

　　使用 SSH 克隆 Git 仓库且 SSH 密钥有密码短语时，远程运行时 VS Code 拉取和同步功能可能挂起。

请使用无密码短语的 SSH 密钥、通过 HTTPS 克隆，或从命令行运行 `git push`。

### 解决缺少依赖项的错误 {#resolving-errors-about-missing-dependencies}

　　某些扩展依赖 WSL Linux 发行版基本安装中不存在的库。可以使用包管理器向 Linux 发行版添加库。Ubuntu 和 Debian 系发行版运行 `sudo apt-get install <package>` 安装所需库。其他安装详情请查阅扩展或错误消息中运行时的文档。

### 本地绝对路径设置在远程应用时失败 {#local-absolute-path-settings-fail-when-applied-remotely}

　　VS Code 本地用户设置连接远程终结点时会复用。这保持用户体验一致，但本地机器与每个主机/容器/WSL 的目标位置不同，绝对路径设置可能需要不同值。

**解决方案**：连接远程终结点后，可以从命令面板（`F1`）运行 **Preferences: Open Remote Settings** 命令，或在设置编辑器选择 **远程** 选项卡，设置终结点特定设置。连接时这些设置会覆盖本地设置。

### 需要在远程终结点安装本地 VSIX {#need-to-install-local-vsix-on-remote-endpoint}

　　开发期间或扩展作者请求测试修复时，可能需要在远程机器安装本地 VSIX。

**解决方案**：连接 SSH 主机、容器或 WSL 后，可以像本地一样安装 VSIX。从命令面板（`F1`）运行 **Extensions: Install from VSIX...** 命令。也可以向 `settings.json` 添加 `"extensions.autoUpdate": false`，防止自动更新到 Marketplace 最新版本。远程环境开发和测试扩展详情请参阅[支持远程开发](https://code.visualstudio.com/api/advanced-topics/remote-extensions)。

### 浏览器无法在本地打开 {#browser-does-not-open-locally}

　　某些扩展使用外部 node 模块或自定义代码启动浏览器窗口，可能导致扩展在远程而不是本地启动浏览器。

**解决方案**：扩展可以使用 `vscode.env.openExternal` API 解决。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#opening-something-in-a-local-browser-or-application)。

### 剪贴板无法使用 {#clipboard-does-not-work}

　　某些扩展使用 `clipboardy` 等 node 模块集成剪贴板，可能导致在远程侧错误集成。

**解决方案**：扩展可以改用 VS Code 剪贴板 API。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#using-the-clipboard)。

### 无法从浏览器或应用程序访问本地 Web 服务器 {#cannot-access-local-web-server-from-browser-or-application}

　　在容器、SSH 主机或 GitHub Codespaces 中工作时，浏览器连接的端口可能被阻止。

**解决方案**：扩展可以使用 `vscode.env.openExternal` 或 `vscode.env.asExternalUri` API（自动转发 localhost 端口）。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#opening-something-in-a-local-browser-or-application)。变通方法是使用 **Forward a Port** 命令手动转发。

### Webview 内容不显示 {#webview-contents-do-not-appear}

　　扩展 Webview 内容使用 `iframe` 连接本地 Web 服务器时，端口可能被阻止。扩展硬编码 `vscode-resource://` URI 而不是使用 `asWebviewUri` 时，内容可能在 Codespaces 浏览器编辑器中不显示。

**解决方案**：扩展可以使用 `webview.asWebviewUri` 解决 `vscode-resource://` URI 问题。

端口被阻止时，最好使用 [Webview 消息传递](https://code.visualstudio.com/api/extension-guides/webview#scripts-and-message-passing) API。变通方法是使用 `vscode.env.asExternalUri` 让 Webview 连接 VS Code 启动的 localhost Web 服务器。但 Codespaces 浏览器编辑器目前阻止此操作（[MicrosoftDocs/vscodespaces#11](https://github.com/MicrosoftDocs/vscodespaces/issues/11)）。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#workarounds-for-using-localhost-from-a-webview)。

### localhost 端口被阻止 {#blocked-localhost-ports}

　　尝试从外部应用连接 localhost 端口时，端口可能被阻止。

**解决方案**：VS Code 1.40 引入了 `vscode.env.asExternalUri` API，扩展可以程序化转发任意端口。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#forwarding-localhost)。变通方法是使用 **Forward a Port** 命令手动转发。

### 存储扩展数据时出错 {#errors-storing-extension-data}

　　扩展可能尝试在 Linux 上查找 `~/.config/Code` 文件夹持久保存全局数据。文件夹可能不存在，导致扩展抛出 `ENOENT: no such file or directory, open '/root/.config/Code/User/filename-goes-here` 等错误。

**解决方案**：扩展可以使用 `context.globalStorageUri` 或 `context.storageUri` 属性。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#persisting-extension-data-or-state)。

### 无法登录或每次连接新终结点都要登录 {#cannot-sign-in-have-to-sign-in-each-time-i-connect-to-a-new-endpoint}

　　需要登录的扩展可能使用自己的代码持久保存机密。代码可能因缺少依赖项失败。即使成功，机密也存储在远程，意味着每个新终结点都需要登录。

**解决方案**：扩展可以使用 [SecretStorage API](https://code.visualstudio.com/api/references/vscode-api#SecretStorage)。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#persisting-secrets)。

### 不兼容的扩展阻止 VS Code 连接 {#an-incompatible-extension-prevents-vs-code-from-connecting}

　　远程主机、容器或 WSL 中安装了不兼容扩展时，VS Code Server 可能因不兼容而挂起或崩溃。扩展立即激活时，可能阻止连接和卸载。

**解决方案**：手动删除远程扩展文件夹：

1. 容器请确保 `devcontainer.json` 不再引用故障扩展。
2. 使用单独终端/命令提示符连接远程主机、容器或 WSL。
   * SSH 或 WSL 请相应连接（运行 `ssh` 连接服务器或打开 WSL 终端）。
   * 容器请通过 `docker ps -a` 找到容器 ID。容器已停止时运行 `docker run -it <id> /bin/sh`；运行中时运行 `docker exec -it <id> /bin/sh`。
3. 连接后，稳定版运行 `rm -rf ~/.vscode-server/extensions`，Insiders 运行 `rm -rf ~/.vscode-server-insiders/extensions`，删除所有扩展。

### 随附或获取预构建本机模块的扩展失败 {#extensions-that-ship-or-acquire-pre-built-native-modules-fail}

　　随 VS Code 扩展捆绑（或动态获取）的本机模块必须[使用 Electron 的 `electron-rebuild`](https://electronjs.org/docs/tutorial/using-native-node-modules) 重新编译。但 VS Code Server 运行标准（非 Electron）Node.js，远程使用时二进制可能失败。

**解决方案**：需要修改扩展。扩展必须包含（或动态获取）Electron 和标准 Node.js 两套二进制，并在激活函数中检查 `context.executionContext === vscode.ExtensionExecutionContext.Remote` 以设置正确二进制。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#using-native-node.js-modules)。

### 扩展仅在非 x86_64 主机或 Alpine Linux 上失败 {#extension-only-fails-on-non-x86_64-hosts-or-alpine-linux}

　　扩展在 Debian 9+、Ubuntu 16.04+ 或 RHEL/CentOS 7+ 远程 SSH 主机、容器或 WSL 上工作，但在受支持的非 x86_64 主机（例如 ARMv7l）或 Alpine Linux 容器上失败，可能只包含不支持这些平台的本机代码或运行时。例如只包含 x86_64 编译版本。Alpine Linux 中，包含的本机代码或运行时可能因 `libc` 实现差异（Alpine 使用 `musl`，其他发行版使用 `glibc`）而无法工作。

**解决方案**：扩展需要选择支持这些平台，编译/包含额外目标的二进制。某些第三方 npm 模块也可能包含导致问题的本机代码，可能需要与模块作者合作添加编译目标。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#supporting-nonx8664-hosts-or-alpine-linux-containers)。

### 扩展因缺少模块而失败 {#extensions-fail-due-to-missing-modules}

　　依赖 Electron 或 VS Code 基础模块（扩展 API 未公开）且未提供后备的扩展，远程运行可能失败。开发者工具控制台可能显示 `original-fs` 未找到等错误。

**解决方案**：移除对 Electron 模块的依赖或提供后备。详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions#avoid-using-electron-modules)。

### 无法访问或传输远程工作区文件到本地机器 {#cannot-access-transfer-remote-workspace-files-to-local-machines}

　　在外部应用中打开工作区文件的扩展可能出错，因为外部应用无法直接访问远程文件。

**解决方案**：创建在本地运行的“UI”扩展时，可以使用 `vscode.workspace.fs` API 与远程工作区文件系统交互。然后将其作为“工作区”扩展的依赖，并按需通过命令调用。扩展类型及通过命令通信的详情请参阅[扩展作者指南](https://code.visualstudio.com/api/advanced-topics/remote-extensions)。

### 无法从扩展访问连接的设备 {#cannot-access-attached-device-from-extension}

　　访问本地连接设备的扩展在远程运行时无法连接这些设备。

**解决方案**：目前没有。我们正在研究最佳解决方法。

### 远程安装的扩展无法连接 Internet {#extensions-fail-to-connect-to-the-internet-when-installed-remotely}

　　远程扩展使用在远程环境无效的本地代理配置时可能无法连接。

**解决方案**：配置远程环境使用自己的代理设置：

1. 连接远程环境时，打开设置并选择 **远程** 选项卡。
2. 禁用 **Http: Use Local Proxy Configuration**（`http.useLocalProxyConfiguration`）。
3. 确保远程环境可以访问 Internet。需要代理时，在 **远程** 设置中配置 **Http: Proxy**（`http.proxy`），或在启动远程服务器的环境中设置 `HTTP_PROXY` 或 `HTTPS_PROXY`。

更改环境变量后请重启远程服务器以应用更改。

## 问题和反馈 {#questions-and-feedback}

### 报告问题 {#reporting-issues}

　　遇到远程开发扩展问题，请收集正确日志，以便帮助[诊断问题](https://aka.ms/vscode-remote/issues/new)。

每个远程扩展都有查看日志的命令。

可以使用命令面板（`F1`）中的 **Remote-SSH: Show Log** 获取 Remote - SSH 扩展日志。报告 Remote - SSH 问题时，请同时确认可以从外部终端（不使用 Remote - SSH）SSH 到机器。

类似地，可以使用 **Dev Containers: Show Container Log** 获取 Dev Containers 扩展日志。

WSL 扩展日志使用 **WSL: Show Log**。也请检查问题是否在上游 [WSL 仓库](https://github.com/microsoft/WSL/issues)跟踪（而不是 WSL 扩展导致）。

　　其他扩展远程使用时出现问题（例如其他扩展在远程上下文加载或安装不正确），可以从 **远程扩展宿主** 输出通道（**Output: Focus on Output View**）获取日志，并从下拉列表选择 **Log (Remote Extension Host)**。

> **注意**：只看到 **Log (Extension Host)** 时，这是本地扩展宿主，远程扩展宿主未启动。日志通道仅在日志文件创建后创建，因此远程扩展宿主未启动时不会创建日志文件，也不会显示在输出视图中。这仍是有用的议题信息。
