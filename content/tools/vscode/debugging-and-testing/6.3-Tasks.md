# 6.3 任务

　　许多工具可以自动执行 lint、构建、打包、测试或部署等任务，例如 [TypeScript 编译器](https://www.typescriptlang.org/)、[ESLint](https://eslint.org/)、[TSLint](https://palantir.github.io/tslint/) 等 linter，以及 [Make](https://en.wikipedia.org/wiki/Make_software)、[Ant](https://ant.apache.org/)、[Gulp](https://gulpjs.com/)、[Jake](https://jakejs.com/)、[Rake](https://ruby.github.io/rake/) 和 [MSBuild](https://github.com/microsoft/msbuild) 等构建系统。

![VS Code 可以与多种外部工具通信](../images/tasks_hero.png)

　　这些工具大多从命令行运行，自动执行内层软件开发循环（编辑、编译、测试和调试）内外的任务。鉴于它们在开发生命周期中的重要性，能够从 VS Code 内部运行工具并分析结果很有帮助。VS Code 任务可以配置为运行脚本和启动进程，从而无需输入命令行或编写新代码即可在 VS Code 内使用这些现有工具。工作区或文件夹特定任务在 `.vscode/tasks.json` 文件中配置。

　　扩展也可以通过[任务提供程序](https://code.visualstudio.com/api/extension-guides/task-provider)贡献任务，这些贡献任务可以添加 `tasks.json` 中定义的工作区特定配置。

> **注意**：任务支持仅在工作区文件夹中可用，编辑单个文件时不可用。

## TypeScript Hello World {#typescript-hello-world}

从一个简单的“Hello World”TypeScript 程序开始，将其编译为 JavaScript。

创建空文件夹 `mytask`，生成 `tsconfig.json`，然后从该文件夹启动 VS Code：

```bash
mkdir mytask
cd mytask
tsc --init
code .
```

创建 `HelloWorld.ts`：

```ts
function sayHello(name: string): void {
    console.log(`Hello ${name}!`);
}

sayHello('Dave');
```

按 `Ctrl + Shift + B` 或从全局 **终端** 菜单运行 **运行生成任务**，会显示选择器：

![TypeScript 生成任务](../images/typescript-build.png)

第一个条目执行 TypeScript 编译器并生成 `HelloWorld.js`；第二个条目以监视模式启动编译器，每次保存 `HelloWorld.ts` 都会重新生成 `HelloWorld.js`。

也可以将 TypeScript 构建或监视任务设为默认生成任务，使 **运行生成任务**（`Ctrl + Shift + B`）直接执行。从 **终端** 菜单选择 **配置默认生成任务**，选择 **tsc: build** 或 **tsc: watch**。VS Code 会生成 `tasks.json`：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "type": "typescript",
            "tsconfig": "tsconfig.json",
            "problemMatcher": [
                "$tsc"
            ],
            "group": {
                "kind": "build",
                "isDefault": true
            }
        }
    ]
}
```

　　此示例没有定义新任务，而是将 TypeScript 扩展贡献的 **tsc: build** 任务标记为默认生成任务。现在按 `Ctrl + Shift + B` 即可执行 TypeScript 编译器。

## 任务自动检测 {#task-auto-detection}

　　VS Code 目前自动检测 Gulp、Grunt、Jake 和 npm 任务。正在与相应扩展作者合作添加 Maven 和 C# `dotnet` 命令支持。使用 Node.js 开发 JavaScript 应用时，通常有描述依赖和脚本的 `package.json`。克隆 [eslint-starter](https://github.com/spicydonuts/eslint-starter) 示例后，从全局菜单执行 **运行任务** 会显示任务列表。

![ESLint starter 任务](../images/eslint-starter.png)

　　运行 `npm install` 安装必要模块。打开 `server.js` 并在语句末尾添加分号（ESLint starter 假设语句不带分号），再次执行 **运行任务**，选择 **npm: lint**。提示选择问题匹配器时选择 **ESLint stylish**：

![ESLint 问题匹配器选择](../images/eslint-problem-matcher-selection.png)

执行任务会产生一个错误，显示在 **问题** 视图中：

![ESLint 问题](../images/eslint-problem.png)

VS Code 还会创建以下 `tasks.json`：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "type": "npm",
            "script": "lint",
            "problemMatcher": [
                "$eslint-stylish"
            ]
        }
    ]
}
```

　　这指示 VS Code 使用 ESLint stylish 格式扫描 **npm lint** 脚本输出中的问题。

　　Gulp、Grunt 和 Jake 的自动检测方式相同。以下是 [vscode-node-debug](https://github.com/microsoft/vscode-node-debug) 扩展检测到的任务示例。

![Gulp 任务自动检测](../images/gulp-auto-detect.png)

> **提示**：可以通过 **快速打开**（`Ctrl + P`）输入 `task`、空格和命令名运行任务，例如 `task lint`。

可以使用以下设置禁用自动检测：

```json
{
    "js/ts.tsc.autoDetect": "off",
    "grunt.autoDetect": "off",
    "jake.autoDetect": "off",
    "gulp.autoDetect": "off",
    "npm.autoDetect": "off"
}
```

## 自定义任务 {#custom-tasks}

　　并非所有任务或脚本都能自动检测，有时需要定义自定义任务。假设有一个运行测试的脚本，Linux 和 macOS 上为 `test.sh`，Windows 上为 `test.cmd`。从全局 **终端** 菜单运行 **配置任务**，选择 **从模板创建 tasks.json 文件**，打开选择器：

![配置任务运行器](../images/configure-task-runner.png)

> **注意**：如果看不到任务运行器模板列表，可能文件夹中已有 `tasks.json`，其内容会在编辑器中打开。关闭文件，删除或重命名后再试。

　　选择 **Others** 创建自定义任务，打开任务骨架。替换为：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "label": "Run tests",
            "type": "shell",
            "command": "./scripts/test.sh",
            "windows": {
                "command": ".\\scripts\\test.cmd"
            },
            "group": "test",
            "presentation": {
                "reveal": "always",
                "panel": "new"
            }
        }
    ]
}
```

任务属性含义：

* **label**：用户界面中显示的任务标签。
* **type**：任务类型。自定义任务可以是 `shell` 或 `process`。`shell` 将命令解释为 shell 命令（bash、cmd 或 PowerShell）；`process` 将命令解释为要执行的进程。
* **command**：实际执行的命令。
* **windows**：Windows 特定属性，在 Windows 上替代默认属性。也可以使用 `linux` 和 `osx`。
* **group**：任务所属组。示例属于 `test` 组，可通过命令面板的 **运行测试任务** 执行。
* **presentation**：控制任务输出在 UI 中的处理方式。示例中终端 `always` 显示，每次任务运行创建 `new` 终端。
* **options**：覆盖 `cwd`（当前工作目录）、`env`（环境变量）或 `shell`（默认 shell）。可以按任务、全局或按平台设置。这里配置的环境变量只能在任务脚本或进程中引用，不会在 `args`、`command` 或其他任务属性中解析。
* **runOptions**：定义任务运行时间和方式。
* **hide**：从运行任务快速选择中隐藏任务，适合复合任务中不能独立运行的元素。

　　在 `tasks.json` 中使用 IntelliSense 可以查看所有属性。按 **触发建议**（`Ctrl + Space`）显示建议，悬停或使用 **阅读更多...**（“i”）浮出控件查看说明。

![tasks.json IntelliSense](../images/tasks-intellisense.png)

　　也可以查看 [tasks.json 架构](../../editor/3.4-Reference/3.4.4-TasksAppendix/)。

　　命令和参数包含空格或 `$` 等特殊字符时，shell 命令需要特殊处理。默认行为：

* 只提供命令时，任务系统原样传给底层 shell。命令需要引号或转义才能正常工作时，命令本身必须包含正确引号或转义字符。例如，列出名称含空格的文件夹，bash 中命令应为 `ls 'folder with spaces'`。

```json
{
  "label": "dir",
  "type": "shell",
  "command": "dir 'folder with spaces'"
}
```

* 提供命令和参数时，命令或参数含空格则使用单引号，`cmd.exe` 使用双引号。以下命令在 PowerShell 中执行为 `dir 'folder with spaces'`。

```json
{
  "label": "dir",
  "type": "shell",
  "command": "dir",
  "args": [
    "folder with spaces"
  ]
}
```

* 要控制参数引用方式，参数可以使用指定值和引用样式的字面量。以下示例对含空格参数使用转义而不是引号：

```json
{
  "label": "dir",
  "type": "shell",
  "command": "dir",
  "args": [
    {
      "value": "folder with spaces",
      "quoting": "escape"
    }
  ]
}
```

除转义外，还支持：

* **strong**：使用 shell 强引用机制，抑制字符串内所有求值。PowerShell 以及 Linux/macOS shell 使用单引号（`'`），cmd.exe 使用 `"`。
* **weak**：使用 shell 弱引用机制，仍会求值字符串内表达式（例如环境变量）。PowerShell 以及 Linux/macOS shell 使用双引号（`"`），cmd.exe 不支持弱引用，VS Code 也使用 `"`。

　　命令本身含空格时，VS Code 默认也会强引用命令。与参数一样，可以使用相同字面量样式控制命令引用。

　　还可以通过命令面板（`Ctrl + Shift + P`）访问任务命令，筛选“task”查看各种任务相关命令。

![命令面板中的任务](../images/command-palette.png)

### 复合任务 {#compound-tasks}

　　可以使用 `dependsOn` 将简单任务组合为复合任务。例如客户端和服务器文件夹都包含构建脚本，可以创建在两个终端中启动构建的任务。`dependsOn` 列出多个任务时默认并行执行。

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "Client Build",
            "command": "gulp",
            "args": ["build"],
            "options": {
                "cwd": "${workspaceFolder}/client"
            }
        },
        {
            "label": "Server Build",
            "command": "gulp",
            "args": ["build"],
            "options": {
                "cwd": "${workspaceFolder}/server"
            }
        },
        {
            "label": "Build",
            "dependsOn": ["Client Build", "Server Build"]
        }
    ]
}
```

　　指定 `"dependsOrder": "sequence"` 时，依赖按 `dependsOn` 中顺序执行。`dependsOrder: sequence` 中使用的后台/监视任务必须有能跟踪“完成”状态的问题匹配器。以下任务依次运行 Two、Three、One：

```json
{
    "label": "One",
    "type": "shell",
    "command": "echo Hello ",
    "dependsOrder": "sequence",
    "dependsOn":[
        "Two",
        "Three"
    ]
}
```

### 用户级任务 {#user-level-tasks}

　　使用 **Tasks: Open User Tasks** 命令创建不绑定特定工作区或文件夹的用户级任务。这里只能使用 `shell` 和 `process` 任务，其他任务类型需要工作区信息。

## 输出行为 {#output-behavior}

　　有时需要控制运行任务时集成终端面板的行为，例如最大化编辑器空间，只在认为有问题时查看任务输出。可以使用任务的 `presentation` 属性：

* **reveal**：控制是否将集成终端面板带到前台。值：
  * `always`：始终带到前台（默认）。
  * `never`：用户必须通过 **视图** > **终端** 命令（`Ctrl + 反引号`）显式带到前台。
  * `silent`：仅当输出不扫描错误和警告时带到前台。
* **revealProblems**：控制运行任务时是否显示问题面板，优先于 `reveal`。默认 `never`。
  * `always`：执行任务时始终显示问题面板。
  * `onProblem`：发现问题时显示。
  * `never`：从不显示。
* **focus**：终端是否获得输入焦点。默认 `false`。
* **echo**：是否在终端回显执行的命令。默认 `true`。
* **showReuseMessage**：是否显示“Terminal will be reused by tasks, press any key to close it”消息。
* **panel**：终端实例是否在任务运行之间共享：
  * `shared`：共享终端，其他任务输出添加到同一终端。
  * `dedicated`：终端专用于特定任务，再次执行该任务时复用；不同任务输出使用不同终端。
  * `new`：每次执行都使用新的干净终端。
* **clear**：运行任务前是否清空终端。默认 `false`。
* **close**：任务退出时是否关闭终端。默认 `false`。
* **group**：是否在特定终端组中使用拆分窗格执行。同一组（字符串值）的任务使用拆分终端而不是新面板。

　　也可以修改自动检测任务的终端面板行为。例如修改 ESLint 示例中 **npm: run lint** 的输出行为：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "type": "npm",
            "script": "lint",
            "problemMatcher": [
                "$eslint-stylish"
            ],
            "presentation": {
                "reveal": "never"
            }
        }
    ]
}

```

　　也可以混合自定义任务和检测任务配置：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "type": "npm",
            "script": "lint",
            "problemMatcher": [
                "$eslint-stylish"
            ],
            "presentation": {
                "reveal": "never"
            }
        },
        {
            "label": "Run tests",
            "type": "shell",
            "command": "./scripts/test.sh",
            "windows": {
                "command": ".\\scripts\\test.cmd"
            },
            "group": "test",
            "presentation": {
                "reveal": "always",
                "panel": "new"
            }
        }
    ]
}

```

## 运行行为 {#run-behavior}

使用 `runOptions` 指定任务运行行为：

* **reevaluateOnRerun**：使用 **重新运行上次任务** 命令执行任务时如何求值变量。默认 `true`，重新运行时重新求值；设为 `false` 时使用上次运行的解析值。
* **runOn**：任务运行时机。
  * `default`：仅通过 **运行任务** 命令执行。
  * `folderOpen`：打开包含文件夹时运行。请参阅[控制自动任务执行](#control-automatic-task-execution)。
* **instanceLimit**：允许同时运行的任务实例数，默认 `1`。
* **instancePolicy**：达到 `instanceLimit` 时的行为：
  * `prompt`：提示用户终止哪个实例（默认）。
  * `silent`：不启动新实例（静默）。
  * `terminateNewest`：终止最新运行实例。
  * `terminateOldest`：终止最旧运行实例。
  * `warn`：不启动新实例（显示警告）。

### 控制自动任务执行 {#control-automatic-task-execution}

　　`task.allowAutomaticTasks` 设置控制打开工作区时是否允许 `"runOn": "folderOpen"` 任务自动运行。无论此设置如何，自动任务从不在[不受信任工作区](../../editor/3.2-WriteCode/3.2.8-Workspaces/3.2.8.3-WorkspaceTrust/)中运行。

设置接受两个值：

* **off**（默认）：不运行自动任务。如果尚未为当前工作区做出选择，会提示一次 **允许** 或 **禁止**。选择 **禁止**（或显式设置为 `off`）后任务不会运行，也不再提示。
* **on**：打开受信任工作区时始终自动运行任务，不提示。

```json
{
    "task.allowAutomaticTasks": "off"
}
```

　　也可以随时使用命令面板中的 **Tasks: Manage Automatic Tasks** 命令，为当前工作区选择 **允许自动任务** 或 **禁止自动任务**。

## 自定义自动检测的任务 {#customizing-auto-detected-tasks}

　　可以在 `tasks.json` 中自定义自动检测任务，通常用于修改 presentation 属性或附加问题匹配器扫描输出。可以从 **运行任务** 列表按右侧齿轮图标直接将任务引用插入 `tasks.json`。假设有以下使用 ESLint 检查 JavaScript 的 Gulp 文件（来自 [gulp-eslint](https://github.com/adametry/gulp-eslint)）：

```js
const gulp = require('gulp');
const eslint = require('gulp-eslint');

gulp.task('lint', () => {
    // ESLint 忽略 "node_modules" 路径中的文件。
    // 因此最好让 gulp 也忽略该目录。
    // 还要确保从任务返回流；
    // 否则任务可能在流完成前结束。
    return gulp.src(['**/*.js','!node_modules/**'])
        // eslint() 将 lint 输出附加到文件对象的 "eslint" 属性，
        // 以便其他模块使用。
        .pipe(eslint())
        // eslint.format() 将 lint 结果输出到控制台。
        // 也可以使用 eslint.formatEach()（见文档）。
        .pipe(eslint.format())
        // 要让 lint 错误时进程以错误代码 (1) 退出，
        // 请返回流并最后管道到 failAfterError。
        .pipe(eslint.failAfterError());
});

gulp.task('default', ['lint'], function () {
    // 仅在 lint 任务成功时运行...
});
```

从全局 **终端** 菜单执行 **运行任务** 会显示选择器：

![配置任务](../images/configure-tasks.png)

按齿轮图标会创建以下 `tasks.json`：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "type": "gulp",
            "task": "default",
            "problemMatcher": []
        }
    ]
}
```

　　通常接下来会添加问题匹配器（例如 `$eslint-stylish`）或修改 presentation 设置。

## 使用问题匹配器处理任务输出 {#processing-task-output-with-problem-matchers}

　　VS Code 可以使用问题匹配器处理任务输出。问题匹配器扫描任务输出中的已知警告或错误字符串，并在编辑器和问题面板中内联报告。VS Code 自带多个问题匹配器：

* **TypeScript**：`$tsc` 假设输出文件名相对于打开的文件夹。
* **TypeScript Watch**：`$tsc-watch` 匹配 `tsc` 编译器监视模式报告的问题。
* **JSHint**：`$jshint` 假设文件名报告为绝对路径。
* **JSHint Stylish**：`$jshint-stylish` 假设文件名报告为绝对路径。
* **ESLint Compact**：`$eslint-compact` 假设输出文件名相对于打开的文件夹。
* **ESLint Stylish**：`$eslint-stylish` 假设输出文件名相对于打开的文件夹。
* **Go**：`$go` 匹配 `go` 编译器报告的问题，假设文件名相对于打开的文件夹。
* **CSharp 和 VB 编译器**：`$mscompile` 假设文件名报告为绝对路径。
* **Lessc 编译器**：`$lessc` 假设文件名报告为绝对路径。
* **Node Sass 编译器**：`$node-sass` 假设文件名报告为绝对路径。

　　也可以创建自己的问题匹配器，详见[定义问题匹配器](#defining-a-problem-matcher)。

## 将键盘快捷键绑定到任务 {#binding-keyboard-shortcuts-to-tasks}

　　需要频繁运行任务时，可以为其定义快捷键。例如将 `Ctrl+H` 绑定到 **Run tests** 任务，在 `keybindings.json` 中添加：

```json
{
    "key": "ctrl+h",
    "command": "workbench.action.tasks.runTask",
    "args": "Run tests"
}
```

## 变量替换 {#variable-substitution}

　　编写任务配置时，预定义变量很有用，例如活动文件 `${file}` 或工作区根 `${workspaceFolder}`。VS Code 支持 `tasks.json` 字符串中的变量替换，完整列表请参阅[变量参考](../../editor/3.4-Reference/3.4.3-SubstitutionVariables/)。

> **注意**：并非所有属性都接受变量替换。只有 `command`、`args` 和 `options` 支持。

以下自定义任务将当前打开文件传给 TypeScript 编译器：

```json
{
    "label": "TypeScript compile",
    "type": "shell",
    "command": "tsc ${file}",
    "problemMatcher": [
        "$tsc"
    ]
}
```

　　类似地，可以通过 `${config:...}` 前缀引用项目配置设置。例如 `${config:python.formatting.autopep8Path}` 返回 Python 扩展的 `formatting.autopep8Path` 设置。

以下任务使用该设置定义的 autopep8 可执行文件处理当前文件：

```json
{
    "label": "autopep8 current file",
    "type": "process",
    "command": "${config:python.formatting.autopep8Path}",
    "args": [
        "--in-place",
        "${file}"
    ]
}
```

　　要为 `tasks.json` 或 `launch.json` 指定 Python 扩展使用的解释器，可以使用 `${command:python.interpreterPath}`。

　　简单变量替换不够时，可以在 `tasks.json` 中添加 `inputs` 节获取用户输入。

![输入示例](../images/run-input-example.gif)

`inputs` 详情请参阅[变量参考](../../editor/3.4-Reference/3.4.3-SubstitutionVariables/)。

## 操作系统特定属性 {#operating-system-specific-properties}

　　任务系统支持定义操作系统特定值（例如要执行的命令）。在 `tasks.json` 中放入操作系统特定字面量并指定相应属性。

以下示例使用 Node.js 可执行文件，并在 Windows 和 Linux 上不同处理：

```json
{
    "label": "Run Node",
    "type": "process",
    "windows": {
        "command": "C:\\Program Files\\nodejs\\node.exe"
    },
    "linux": {
        "command": "/usr/bin/node"
    }
}
```

　　有效操作系统属性为 `windows`、`linux` 和 `osx`（macOS）。操作系统特定作用域中的属性覆盖任务或全局作用域属性。

## 全局任务 {#global-tasks}

　　任务属性也可以在全局作用域定义。存在时，除非特定任务定义具有不同值的相同属性，否则使用全局值。以下示例定义全局 `presentation`，所有任务都在新面板中执行：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "presentation": {
        "panel": "new"
    },
    "tasks": [
        {
            "label": "TS - Compile current file",
            "type": "shell",
            "command": "tsc ${file}",
            "problemMatcher": [
                "$tsc"
            ]
        }
    ]
}
```

> **提示**：要访问全局 `tasks.json`，请在命令面板（`Ctrl + Shift + P`）运行 **Tasks: Open User Tasks** 命令。

### PowerShell 中的字符转义 {#character-escaping-in-powershell}

　　默认 shell 为 PowerShell 或任务配置使用 PowerShell 时，可能看到意外空格和引号转义。意外转义只发生在 cmdlet 上，因为 VS Code 不知道命令是否包含 cmdlet。示例 1 显示在 PowerShell 中无法工作的转义；示例 2 是跨平台最佳方式；无法遵循示例 2 时需要示例 3 的手动转义。

```json
"tasks": [
    {
        "label": "PowerShell example 1 (unexpected escaping)",
        "type": "shell",
        "command": "Get-ChildItem \"Folder With Spaces\""
    },
    {
        "label": "PowerShell example 2 (expected escaping)",
        "type": "shell",
        "command": "Get-ChildItem",
        "args": ["Folder With Spaces"]
    },
    {
        "label": "PowerShell example 3 (manual escaping)",
        "type": "shell",
        "command": "& Get-ChildItem \\\"Folder With Spaces\\\""
    }
]
```

## 更改任务输出的编码 {#changing-the-encoding-for-a-task-output}

　　任务经常处理磁盘文件。文件编码与系统编码不同时，需要让任务命令知道使用哪种编码。这取决于操作系统和 shell，没有通用解决方案。

　　需要调整编码时，请检查是否应更改操作系统默认编码，或至少调整 shell 配置文件。仅需为特定任务调整时，请在任务命令行添加操作系统特定编码命令。以下示例用于默认代码页 437 的 Windows，任务列出包含西里尔字符的文件，因此需要代码页 866。假设默认 shell 为 `cmd.exe`：

```json
{
    // 有关 tasks.json 格式的文档，请参阅 https://go.microsoft.com/fwlink/?LinkId=733558
    "version": "2.0.0",
    "tasks": [
        {
            "label": "more",
            "type": "shell",
            "command": "chcp 866 && more russian.txt",
            "problemMatcher": []
        }
    ]
}
```

　　在 PowerShell 中执行时命令应写成 `chcp 866; more russian.txt`。Linux 和 macOS 上可以使用 `locale` 命令检查区域设置并调整必要环境变量。

## 定义问题匹配器 {#defining-a-problem-matcher}

　　VS Code 自带常见问题匹配器，但许多编译器和 lint 工具都有自己的错误和警告格式，可能需要创建自定义匹配器。

假设 `helloWorld.c` 中将 **printf** 误写为 **prinft**，用 [gcc](https://gcc.gnu.org/) 编译产生：

```bash
helloWorld.c:5:3: warning: implicit declaration of function ‘prinft’
```

　　我们希望问题匹配器捕获消息并在 VS Code 中显示问题。问题匹配器高度依赖[正则表达式](https://en.wikipedia.org/wiki/Regular_expression)。

> **提示**：[RegEx101 playground](https://regex101.com/)支持 ECMAScript（JavaScript）风格，是开发和测试正则表达式的好工具。

捕获上述警告（和错误）的匹配器：

```json
{
    // 问题由 cpp 语言服务拥有。
    "owner": "cpp",
    // 报告问题的文件名相对于打开的文件夹。
    "fileLocation": ["relative", "${workspaceFolder}"],
    // 显示为问题来源的名称。
    "source": "gcc",
    // 匹配输出中问题的实际模式。
    "pattern": {
        // 正则表达式。示例匹配：helloWorld.c:5:3: warning: implicit declaration of function ‘printf’ [-Wimplicit-function-declaration]
        "regexp": "^(.*):(\\d+):(\\d+):\\s+(warning|error):\\s+(.*)$",
        // 第一个匹配组匹配相对文件名。
        "file": 1,
        // 第二个匹配组匹配问题所在行。
        "line": 2,
        // 第三个匹配组匹配问题所在列。
        "column": 3,
        // 第四个匹配组匹配问题严重性。可以忽略，此时所有问题都作为错误捕获。
        "severity": 4,
        // 第五个匹配组匹配消息。
        "message": 5
    }
}
```

　　文件、行和消息属性是必需的。`fileLocation` 指定任务输出中匹配的文件路径是 `absolute` 还是 `relative`。任务同时产生绝对和相对路径时，可以使用 `autoDetect`：先测试绝对路径，文件不存在则假定为相对路径。

　　`severity` 指定模式未包含严重性时使用的问题严重性，值为 `error`、`warning` 或 `info`。

完整 `tasks.json`（移除注释）：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "build",
            "command": "gcc",
            "args": ["-Wall", "helloWorld.c", "-o", "helloWorld"],
            "problemMatcher": {
                "owner": "cpp",
                "fileLocation": ["relative", "${workspaceFolder}"],
                "source": "gcc",
                "pattern": {
                    "regexp": "^(.*):(\\d+):(\\d+):\\s+(warning|error):\\s+(.*)$",
                    "file": 1,
                    "line": 2,
                    "column": 3,
                    "severity": 4,
                    "message": 5
                }
            }
        }
    ]
}
```

　　在 VS Code 中运行并按 `Ctrl + Shift + M` 打开问题列表：

![GCC 问题匹配器](../images/problemmatcher.png)

> **注意**：[C/C++ 扩展](https://marketplace.visualstudio.com/items?itemName=ms-vscode.cpptools)包含 GCC 问题匹配器，无需自行定义。

pattern 中还可以使用：

* **location**：问题位置为 line、line,column 或 startLine,startColumn,endLine,endColumn 时，可以使用通用位置匹配组。
* **endLine**：问题结束行的匹配组索引。编译器不提供结束行时可以省略。
* **endColumn**：问题结束列的匹配组索引。编译器不提供结束列时可以省略。
* **code**：问题代码的匹配组索引。编译器不提供代码时可以省略。

　　也可以定义只捕获文件的问题匹配器：将 `pattern` 的可选 `kind` 属性设为 `file`，此时无需 `line` 或 `location`。

> **注意**：`kind` 为 `file` 时，功能 pattern 至少必须提供 `file` 和 `message` 匹配组。未提供 `kind` 或 `kind` 为 `location` 时，还必须提供 `line` 或 `location`。

> **注意**：问题匹配器只解析给定命令的输出。要解析写入单独文件（例如日志文件）的输出，请让运行命令在结束前打印该文件中的行。

## 定义多行问题匹配器 {#defining-a-multiline-problem-matcher}

　　某些工具将源文件问题分散在多行，尤其使用 stylish 报告器时。[ESLint](https://eslint.org/) stylish 模式输出：

```bash
test.js
  1:0   error  Missing "use strict" statement                 strict
✖ 1 problems (1 errors, 0 warnings)
```

　　问题匹配器基于行，因此需要用不同正则表达式捕获文件名（test.js）和实际问题位置与消息（1:0 error...）。

　　为此，将 `pattern` 设为问题模式数组，为每一行定义一个模式。

> **注意**：多行问题匹配器中，模式数组必须从第一个模式开始匹配每一行连续输出。不能跳过中间行，即使没有有用信息。

　　工具输出三行且只需要第一和第三行数据时，模式数组仍需要三个条目。不需要数据的行使用 `{"regexp": "^.*$"}`，不分配捕获组：

```json
"pattern": [
    { "regexp": "^Error:\\s+(.*)$", "message": 1 },
    { "regexp": "^.*$" },
    { "regexp": "^\\s+at\\s+(.*):(\\d+)$", "file": 1, "line": 2 }
]
```

以下模式匹配 ESLint stylish 输出，但仍有问题需要解决。第一个正则表达式捕获文件名，第二个捕获行、列、严重性、消息和错误代码：

```json
{
    "owner": "javascript",
    "fileLocation": ["relative", "${workspaceFolder}"],
    "pattern": [
        {
            "regexp": "^([^\\s].*)$",
            "file": 1
        },
        {
            "regexp": "^\\s+(\\d+):(\\d+)\\s+(error|warning|info)\\s+(.*)\\s\\s+(.*)$",
            "line": 1,
            "column": 2,
            "severity": 3,
            "message": 4,
            "code": 5
        }
    ]
}
```

　　资源有多个问题时此模式无法工作。例如：

```bash
test.js
  1:0   error  Missing "use strict" statement                 strict
  1:9   error  foo is defined but never used                  no-unused-vars
  2:5   error  x is defined but never used                    no-unused-vars
  2:11  error  Missing semicolon                              semi
  3:1   error  "bar" is not defined                           no-undef
  4:1   error  Newline required at end of file but not found  eol-last
✖ 6 problems (6 errors, 0 warnings)
```

　　第一个正则表达式匹配“test.js”，第二个匹配“1:0 error...”。下一行“1:9 error...”被处理但第一个正则表达式不匹配，因此不会捕获问题。

　　要解决此问题，多行模式的最后一个正则表达式可以指定 `loop` 属性。设为 true 时，任务系统会在正则表达式匹配的情况下，将多行匹配器最后一个模式应用于后续输出行。

　　第一个模式捕获的“test.js”信息会与每个匹配 `loop` 模式的后续行组合，创建多个问题。此示例会创建六个问题。

完整 ESLint stylish 问题匹配器：

```json
{
    "owner": "javascript",
    "fileLocation": ["relative", "${workspaceFolder}"],
    "pattern": [
        {
            "regexp": "^([^\\s].*)$",
            "file": 1
        },
        {
            "regexp": "^\\s+(\\d+):(\\d+)\\s+(error|warning|info)\\s+(.*)\\s\\s+(.*)$",
            "line": 1,
            "column": 2,
            "severity": 3,
            "message": 4,
            "code": 5,
            "loop": true
        }
    ]
}
```

> **注意**：同一资源上存在完全相同行和列的多个问题时，只显示一个问题。这适用于所有问题匹配器，不仅是多行匹配器。

## 修改现有问题匹配器 {#modifying-an-existing-problem-matcher}

　　现有问题匹配器接近需求时，可以在 `tasks.json` 中修改。例如 `$tsc-watch` 问题匹配器只应用于已关闭文档，希望应用于所有文档时可以修改：

```json
{
    "type": "npm",
    "script": "watch",
    "problemMatcher": {
        "base": "$tsc-watch",
        "applyTo": "allDocuments"
    },
    "isBackground": true,
}
```

　　其他可修改属性包括 `background`、`fileLocation`、`owner`、`pattern`、`severity` 和 `source`。

## 后台/监视任务 {#background-watching-tasks}

　　某些工具支持在后台运行并监视文件系统，文件更改时触发操作。`Gulp` 通过 [gulp-watch](https://www.npmjs.com/package/gulp-watch) 提供此功能，TypeScript 编译器 `tsc` 通过 `--watch` 命令行选项内置支持。

　　要反馈后台任务在 VS Code 中活动并产生问题结果，问题匹配器必须使用额外信息检测输出中的 `state` 变化。以 `tsc` 为例，监视模式启动时输出：

```bash
> tsc --watch
12:30:36 PM - Compilation complete. Watching for file changes.
```

　　磁盘文件包含问题时输出：

```bash
12:32:35 PM - File change detected. Starting incremental compilation...
src/messages.ts(276,9): error TS2304: Cannot find name 'candidate'.
12:32:35 PM - Compilation complete. Watching for file changes.
```

　　模式如下：

* 输出 `File change detected. Starting incremental compilation...` 时编译器运行。
* 输出 `Compilation complete. Watching for file changes.` 时编译器停止。
* 两个字符串之间报告问题。
* 编译器初始启动时也会运行一次（不打印 `File change detected...`）。

　　问题匹配器可以提供 `background` 属性捕获这些信息。对于 `tsc`：

```json
"background": {
    "activeOnStart": true,
    "beginsPattern": "^\\s*\\d{1,2}:\\d{1,2}:\\d{1,2}(?: AM| PM)? - File change detected\\. Starting incremental compilation\\.\\.\\.",
    "endsPattern": "^\\s*\\d{1,2}:\\d{1,2}:\\d{1,2}(?: AM| PM)? - Compilation complete\\. Watching for file changes\\."
}
```

　　除问题匹配器的 `background` 属性外，任务本身必须标记为 `isBackground`，以便在后台持续运行。

完整 `tsc` 监视任务：

```json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "watch",
            "command": "tsc",
            "args": ["--watch"],
            "isBackground": true,
            "problemMatcher": {
                "owner": "typescript",
                "fileLocation": "relative",
                "pattern": {
                    "regexp": "^([^\\s].*)\\((\\d+|\\d+,\\d+|\\d+,\\d+,\\d+,\\d+)\\):\\s+(error|warning|info)\\s+(TS\\d+)\\s*:\\s*(.*)$",
                    "file": 1,
                    "location": 2,
                    "severity": 3,
                    "code": 4,
                    "message": 5
                },
                "background": {
                    "activeOnStart": true,
                    "beginsPattern": "^\\s*\\d{1,2}:\\d{1,2}:\\d{1,2}(?: AM| PM)? - File change detected\\. Starting incremental compilation\\.\\.\\.",
                    "endsPattern": "^\\s*\\d{1,2}:\\d{1,2}:\\d{1,2}(?: AM| PM)? - Compilation complete\\. Watching for file changes\\."
                }
            }
        }
    ]
}
```

## 常见问题 {#common-questions}

### 任务可以使用与集成终端不同的 shell 吗？ {#can-a-task-use-a-different-shell-than-the-one-specified-for-the-integrated-terminal}

　　可以。可以使用 `terminal.integrated.automationProfile.*` 设置为所有自动化（包括任务）设置 shell：

```json
    "terminal.integrated.automationProfile.windows": {
        "path": "cmd.exe"
    }
```

也可以使用 `options.shell` 覆盖任务 shell，可以按任务、全局或按平台设置。例如 Windows 上使用 cmd.exe：

```json
{
    "version": "2.0.0",
    "windows": {
        "options": {
            "shell": {
                "executable": "cmd.exe",
                "args": [
                    "/d", "/c"
                ]
            }
        }
    },
    ...
```

### 后台任务可以用作 launch.json 中的 prelaunchTask 吗？ {#can-a-background-task-be-used-as-a-prelaunchtask-in-launchjson}

　　可以。后台任务运行到被终止，本身没有“完成”信号。要作为 `prelaunchTask`，必须添加适当的后台 `problemMatcher`，让任务系统和调试系统知道任务“完成”。

任务可以如下：

```json
{
    "type": "npm",
    "script": "watch",
    "problemMatcher": "$tsc-watch",
    "isBackground": true,
}
```

> **注意**：`$tsc-watch` 是**后台**问题匹配器，后台任务需要它。

然后在 `launch.json` 中使用：

```json
{
    "name": "Launch Extension",
    "type": "extensionHost",
    "request": "launch",
    "runtimeExecutable": "${execPath}",
    "args": [
        "--extensionDevelopmentPath=${workspaceRoot}"
    ],
    "stopOnEntry": false,
    "sourceMaps": true,
    "outFiles": [
        "${workspaceRoot}/out/src/**/*.js"
    ],
    "preLaunchTask": "npm: watch"
}
```

### 为什么运行任务时提示“command not found”？ {#why-do-i-get-command-not-found-when-running-a-task}

　　此消息表示终端无法识别要运行的任务命令。通常是因为命令配置在 shell 启动脚本中。任务以非登录、非交互方式运行，因此不会执行 shell 启动脚本。`nvm` 特别以使用启动脚本配置而闻名。

解决方法：

1. 确保命令在 PATH 中，且不需要启动脚本添加到 PATH。这是最彻底、推荐的方法。
2. 为任务做一次性修复，以登录或交互方式运行。不推荐，因为可能有其他后果，但对单个任务可以快速解决。以下示例使用 `bash` shell：

```json
{
    "type": "npm",
    "script": "watch",
    "options": {
        "shell": {
            "args": ["-c", "-l"]
        }
    }
}
```

　　上述 `npm` 任务会像任务系统默认那样使用命令（`-c`）运行 `bash`，但还会以登录 shell（`-l`）运行 `bash`。
