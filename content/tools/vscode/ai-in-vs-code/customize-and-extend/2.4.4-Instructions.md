# 2.4.4 自定义指令

　　自定义指令为智能体提供可复用的项目指导，例如在哪里添加代码、使用哪些库以及运行哪些测试。将这些指导存储在 Markdown 文件中，而不是在每个提示词中重复，并通过源代码管理共享项目指令。

　　先从一个智能体反复遗漏的约定开始。在[智能体自定义编辑器](../2.4.1-Overview/#agent-customizations-editor)中创建指令，然后在新聊天中测试效果，再添加更有针对性的指导。支持的位置、文件语法和设置请参阅[自定义指令参考](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/)。

　　指令用于引导模型，不能保证遵守，也不能替代测试、代码审查或安全控制。它们不适用于输入时的[内联建议](../../../editor/3.2-WriteCode/3.2.3-InlineSuggestions/)。

## 开始使用项目指令 {#get-started-with-project-instructions}

　　打开仓库根目录，并[选择要使用的智能体运行框架](../../choose-models-and-agents/2.3.2-ChooseAnAgentHarness/#select-a-harness)。运行框架决定读取哪些指令文件。例如，在 Copilot 会话中选择 Claude 模型不会切换到 Claude 运行框架。

　　首次设置时，请在当前文件夹中工作，而不是新建工作树，以便测试会话可以访问未提交的指令。

### 创建项目指令 {#create-project-instructions}

1. 从命令面板（`Ctrl + Shift + P`，macOS：`Cmd + Shift + P`）运行 **Chat: Open Customizations**，打开智能体自定义编辑器并选择 **指令** 选项卡。
2. 要添加项目指令文件，请选择 **工作区** 旁的 `+`，然后选择运行框架提供的项目指令文件，例如 `AGENTS.md` 或 `CLAUDE.md`。编辑器会在工作区中创建或打开该文件。

   如果仓库已有项目指令文件，请打开它，而不是创建竞争副本。

3. 添加几条针对重复问题的具体规则。例如，Node.js API 项目可以使用以下指令。请将路径和测试命令替换为仓库中可用的内容。

   ```markdown
   # 项目指令

   * 在 `src/api/routes` 下添加 HTTP 处理程序。
   * 将数据库访问保留在 `src/repositories`，使处理程序可以独立测试。
   * 为行为更改添加或更新测试，并对受影响的测试运行 `npm test -- <test-file>`。
   ```

4. 保存文件。这些项目指令文件不需要 frontmatter。

#### 直接创建文件 {#create-the-file-directly}

　　如果希望在智能体自定义编辑器之外创建文件，请使用运行框架支持的项目指令文件。以下路径相对于仓库根目录。按需创建缺少的文件夹。

| 运行框架 | 项目指令文件 |
|---------|---------------------------|
| Copilot | `.github/copilot-instructions.md` 或 `AGENTS.md` |
| Anthropic Claude | `CLAUDE.md` |
| OpenAI Codex | `AGENTS.md` |
| Local | `.github/copilot-instructions.md` 或 `AGENTS.md` |

　　添加规则、保存文件，并按下面说明验证。`AGENTS.md` 是跨智能体格式，不是 Codex 专用文件。跨运行框架共享同一文件之前，请参阅[支持的格式](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/#supported-formats-and-locations)。

### 验证指令 {#verify-your-instructions}

　　测试一个规则会影响结果的小任务。全程使用相同运行框架和仓库：

1. 从命令面板运行 **Chat: Open Customizations**，选择 **指令**，确认文件已列出。这检查发现，而不是智能体是否遵循规则。
2. 启动新聊天，使测试不依赖创建指令时对话中的指导。
3. 请求一个小更改，不要在提示词中重复规则。对于 API 示例，要求智能体使用项目现有模式添加终结点。
4. 检查响应中的 **引用** 部分（如果可用）是否包含指令文件。如需更多细节，请[在智能体调试日志中检查请求](../../reference-and-help/troubleshooting/2.8.2.2-DebugChatInteractions/#instructions-or-a-prompt-file-are-not-applied)。
5. 审查更改和工具活动。对于示例，检查处理程序添加位置、数据访问方式以及智能体是否运行了相关测试。

　　如果结果符合目标，请审查并提交指令文件，供团队使用。如果不符合，请先[确定文件是被发现、包含还是被遵循](#troubleshoot-instructions)，再添加更多规则。

　　完整的修改前后对比和团队推广工作流请参阅[为代码库配置 AI](../../tutorials-and-guides/2.6.10-AdaptAgentsToYourProject/)。

## 指令如何应用 {#how-instructions-apply}

　　作用域和激活回答不同问题。作用域决定指导在哪里可用以及谁共享它。激活决定指导何时包含在请求中。

| 作用域 | 用途 |
|-------|------------|
| 工作区或仓库 | 通过源代码管理与贡献者共享的项目约定 |
| 用户 | 跨项目的个人偏好，位于运行框架支持的位置 |
| 组织 | 受支持体验的集中管理指导 |

　　从适用于广泛规则的项目指令开始。对于只在代码库部分区域需要的指导，使用有针对性的指令。

| 激活 | 工作方式 |
|------------|--------------|
| 项目范围 | 运行框架包含其项目指令文件中的指导。 |
| 文件模式 | `.instructions.md` 文件使用 `applyTo`，或 Claude 规则文件使用 `paths`，匹配智能体处理的文件。 |
| 任务相关性 | 在 Local 会话中，`description` 让智能体决定是否为任务读取指令文件。这与模式匹配相互独立。 |
| 手动 | 当自动发现或激活不合适时，为特定请求附加指导。 |

　　`AGENTS.md` 等指令文件为现有智能体提供指导，不定义[自定义智能体](../2.4.5-CustomAgents/)。如果需要可复用的多步骤工作流而不是编码约定或项目上下文，请考虑[智能体技能](../2.4.3-AgentSkills/)。在自行编写工作流之前，请[在自定义 Marketplace 中查找现有技能](../2.4.3-AgentSkills/#install-a-skill-from-the-customization-marketplace-preview)。将仓库专用命令和约定保留在项目指令中。

## 将指令应用到特定文件或任务 {#apply-instructions-to-specific-files-or-tasks}

　　将项目范围规则保留在主指令文件中。当测试需要与应用代码不同的约定时，添加有针对性的指导。以下示例将 Python 测试规则限定到 `tests` 目录。

　　在智能体自定义编辑器中选中目标运行框架，按照下面对应运行框架的步骤操作，然后调整路径和规则。

**Copilot 或 Local**

1. 从命令面板运行 **Chat: Open Customizations**，选择 **指令**。
2. 选择 **工作区** 旁的 `+`，选择新建指令文件的操作，而不是 `AGENTS.md` 等全项目文件。
3. 在提示时选择 `.github/instructions`，输入 `python-tests` 作为文件名。
4. 在生成的文件中，添加以下 frontmatter 和指令。

使用 `applyTo` 指定指令适用的文件：

```markdown
---
applyTo: 'tests/**/*.py'
---
# Python 测试

* 重用 `tests/conftest.py` 中的夹具，不要重复设置。
* 将测试命名为 `test_<behavior>_<condition>`。
* 更改测试后运行 `python -m pytest <test-file>`。
```

　　该模式匹配 `tests/test_api.py` 和 `tests/unit/test_api.py`，但不匹配 `src/api.py`。它相对于工作区或项目根目录，而不是 `.github/instructions` 目录。

　　如果希望直接创建文件，请保存为 `.github/instructions/python-tests.instructions.md`。为适用于不同语言、文件夹或任务的指导使用单独的 `.instructions.md` 文件。

　　在 Local 会话中，还可以添加 `description`，例如 `'Use when creating or updating Python tests.'`，用于基于任务的发现。描述不是 `applyTo` 的额外限制。智能体可以按相关性单独加载文件，独立于模式匹配。

**Claude**

1. 在选中 **Claude** 运行框架的情况下打开智能体自定义编辑器，选择 **指令**。
2. 选择 **工作区** 旁的 `+`，选择新建规则文件的操作，而不是全项目 `CLAUDE.md` 文件。
3. 在提示时选择 `.claude/rules`，输入 `python-tests` 作为文件名。
4. 在生成的文件中，添加以下 frontmatter 和指令。

使用 `paths` 列出规则适用的文件模式。模式相对于项目根目录：

```markdown
---
paths:
  - 'tests/**/*.py'
---
# Python 测试

* 重用 `tests/conftest.py` 中的夹具，不要重复设置。
* 将测试命名为 `test_<behavior>_<condition>`。
* 更改测试后运行 `python -m pytest <test-file>`。
```

　　该规则针对 `tests` 下的 Python 文件，包括嵌套目录。没有 `paths` 时，规则普遍适用。

　　如果希望直接创建文件，请保存为 `.claude/rules/python-tests.md`。为适用于不同语言、文件夹或任务的指导使用单独的规则文件。

**Codex**

　　对于嵌套指令，请在选中 **Codex** 运行框架的情况下使用智能体自定义编辑器的 **概述** 部分请求文件：

```text
创建或更新 tests/AGENTS.md，加入 Python 测试约定。
重用 conftest.py 中的夹具，将测试命名为 test_<behavior>_<condition>，
并在更改测试后运行 python -m pytest <test-file>。
保留现有指导，不要更改应用代码。
```

　　使用前审查生成的文件。Codex 使用目录位置，而不是 `applyTo` 或 `paths` 模式，这些文件不需要 YAML frontmatter。将项目范围指令保留在仓库根目录 `AGENTS.md` 中，将有针对性的指导放在相关目录。

例如，`tests/AGENTS.md` 包含：

```markdown
# Python 测试

* 重用 `conftest.py` 中的夹具，不要重复设置。
* 将测试命名为 `test_<behavior>_<condition>`。
* 更改测试后运行 `python -m pytest <test-file>`。
```

　　以 `tests` 作为工作目录启动新的 Codex 会话。Codex 会加载从仓库根目录到该目录路径上的指令。在编辑器中打开测试文件不会更改会话的工作目录。

　　如果希望直接创建文件，请将示例保存为 `tests/AGENTS.md`。

创建文件后：

1. 保存文件，并使用同一运行框架启动新聊天。
2. 要求智能体在匹配目录中添加或更新测试。
3. [验证包含和行为](#verify-your-instructions)。检查测试是否遵循命名和夹具约定，以及智能体是否运行测试命令。

　　更多模式和嵌套文件行为请参阅[指令激活](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/#discovery-and-activation)。

### 将指令附加到单个请求 {#attach-instructions-to-one-request}

　　对于一次性需求，请将指导放入提示词，而不是创建共享规则。

　　要为单个请求复用现有指令文件，请在聊天输入框中选择 **添加上下文**（`+` 图标），并在发送请求前选择该文件。

## 编写有效的指令 {#write-effective-instructions}

　　编写帮助智能体做出项目特定决策的规则，而不是描述仓库中的所有内容。

| 不要写 | 改为写 |
|------------|-------|
| 编写好的测试。 | 重用 `tests/conftest.py` 中的夹具，并在更改测试后运行 `python -m pytest <test-file>`。 |
| 遵循架构。 | 将数据库访问保留在 `src/repositories`，使 HTTP 处理程序可以独立测试。 |
| 遵循我们的风格。 | 使用 `src/errors.ts` 中的现有错误类型，而不是返回错误字符串。 |

* **保持规则简洁。** 每条要求使用简短陈述，并解释不明显的约束。
* **优先提供可操作细节。** 指明智能体应使用的命令、目录、库或现有示例。
* **避免不必要的上下文。** 不要重复格式化程序或 linter 强制执行的规则。将专门指导移出全项目文件。
* **随代码维护指令。** 通过源代码管理审查更改，并在命令、架构或依赖项变化时更新规则。
* **谨慎引用支持文档。** 使用带相对路径和 `/` 分隔符的 Markdown 链接。链接不能保证文档内容会到达模型。请检查[引用文件行为](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/#reference-other-files)。

### 解决冲突指令 {#resolve-conflicting-instructions}

　　保持个人、仓库和组织指导中的共享要求一致。不要依赖通用优先级顺序：[组合规则因运行框架而异](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/#combine-instruction-sources)。

　　如果个人指令要求一个库，而仓库要求另一个库，请删除或缩小冲突的个人规则。不要添加另一条规则来补偿。解决冲突后，在新聊天中重复相同的代表性任务。

## 管理项目和个人指令 {#manage-project-and-personal-instructions}

　　返回智能体自定义编辑器中的 **指令**，查找和编辑现有指令。要添加个人指令，请选择 **用户** 旁的 `+`。按照提示输入运行框架支持的名字和存储位置，保存文件，并在该运行框架的新聊天中验证。

　　用户作用域用于跨项目的个人偏好。除非团队也希望使用，否则不要将个人响应偏好放入共享项目文件。位置和同步限制请参阅[用户指令](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/#user-instructions)。

　　也可以将指令作为[智能体插件](../2.4.2-Plugins/#what-plugins-provide)中的规则组件分发，并与其他智能体、技能或工具一起使用。支持取决于所选运行框架和插件格式。跨客户端共享捆绑包之前，请检查[插件兼容性](../2.4.2-Plugins/#cross-tool-compatibility)。

## 排查指令问题 {#troubleshoot-instructions}

　　更改指导之前，请确定失败阶段：

| 观察到的现象 | 检查内容 |
|------------------|--------|
| 自定义编辑器中未列出文件 | 确认所选运行框架、文件名、受支持位置，以及会话是否使用包含更改的文件夹。 |
| 文件被发现，但任务未包含它 | 检查 frontmatter 错误和激活条件。测试匹配文件，或手动附加指令。对于 Local，请检查适用的[发现设置](../../reference-and-help/reference/2.8.1.6-CustomInstructionsReference/#local-harness-settings)。 |
| 文件已包含，但结果未遵循 | 检查矛盾或模糊的规则。澄清一条规则，在新聊天中重复任务，并比较实际更改和工具活动。 |

　　响应的 **引用** 部分（如果可用）有助于检查包含，而不是遵守情况。详细证据请遵循[指令诊断](../../reference-and-help/troubleshooting/2.8.2.2-DebugChatInteractions/#instructions-or-a-prompt-file-are-not-applied)。复现问题之前请准备日志。
