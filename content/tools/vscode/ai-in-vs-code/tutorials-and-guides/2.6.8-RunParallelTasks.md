# 2.6.8 并行运行任务

　　当两个编码任务相互独立时，可以将每个任务分配给智能体，让两者同时运行，并审查进度。单独对话可以保持指令聚焦，但不一定能保持文件更改隔离。

　　本指南在自己的仓库中选择两个更改，在单独 Git 工作树中运行，分别审查结果，然后整合并重新测试组合更改。请先定义任务及验收标准，并在整个工作流中使用它们。不需要示例项目。

## 前提条件 {#prerequisites}

要遵循本指南，需要：

* 已[设置 AI 功能](../../getting-started/2.1.2-SetUpCopilot/)的 VS Code。
* 可以访问[智能体窗口](../../work-with-ai/2.2.3-AgentsWindow/)和 Copilot 运行框架。
* 至少有一次提交、可用开发环境和现有测试的本地 Git 仓库。
* 完成单个智能体辅助任务的经验。如果不熟悉智能体，请从[智能体快速入门](../../getting-started/2.1.3-AgentsQuickstart/)开始。

## 1. 分离工作 {#1-separate-the-work}

　　从待办事项中选择两个小更改，标记为 **任务 A** 和 **任务 B**。每个任务必须能够针对当前代码独立实现和测试，不等待另一个任务。

为每个任务创建包含以下细节的简介。使用这些简介编写委派提示词并审查结果。

| 细节 | 记录内容 |
|---|---|
| 结果 | 想要的可观察更改，例如必须产生特定结果的输入。 |
| 允许的文件 | 智能体可以编辑的实现和测试文件。 |
| 验收标准 | 证明任务完成的行为或测试结果。 |
| 要保留的行为 | 必须保持不变的现有行为。 |
| 范围之外 | 智能体必须避免的文件和更改，包括另一个任务的实现。 |
| 验证 | 现有测试命令以及验证结果所需的手动检查。 |

　　例如，工具中的解析修复和不相关表单中的验证消息更改可能相互独立。这些是任务边界示例，不是项目需要的功能。请选择仓库中重要的工作。

继续之前比较两个简介：

1. 检查每个任务有不同文件集，并能单独验证。
2. 找出两个任务都不应更改的共享文件，例如依赖清单、API 契约、生成文件和共享样式。
3. 检查任一任务是否依赖另一个任务的输出。如果依赖，请选择其他任务对，或先完成前置任务。

　　不同文件并不总是意味着独立工作。如果两个任务都需要新的 API 响应结构，请先完成并验证共享更改。不要让两个智能体独立设计它。

**检查任务定义：** 你应该能够解释每个任务的成功标准，而无需引用另一个智能体将要做的工作。

## 2. 选择隔离方式 {#2-choose-isolation}

发送提示词之前，选择智能体可以更改的位置：

| 工作安排 | 适用场景 | 文件隔离 |
|---|---|---|
| 嵌套会话 | 相关问题或可共享编辑的协调工作。 | 嵌套会话默认使用父会话的文件夹或工作树。受支持的嵌套会话可以使用其他文件夹或单独工作树。 |
| 使用同一文件夹的单独会话 | 与实现并行的只读调查，或一次运行一个的任务。 | 对话分开，但两个会话可以编辑相同工作文件。 |
| 各自使用新工作树的单独会话 | 希望分别审查和整合的独立实现任务。 | 每个任务有自己的工作文件和分支。整合仍可能产生冲突。 |

　　本演练使用**两个单独会话**，每个都选择**新工作树**。创建另一个聊天或分叉对话本身不会创建另一个工作树。

> **警告**：工作树隔离工作文件，不隔离智能体对你计算机或外部服务的访问。请使用受信任仓库，为每个会话选择权限级别，并在继续前审查[权限和沙盒控制](../../work-with-ai/permissions-and-security/2.2.12.1-ApprovalsAndPermissions/)。工作树会话支持手动审批，不需要跳过工具审批提示的 **全部允许**。

　　可用选项详情请参阅[选择智能体更改位置](../../work-with-ai/2.2.3-AgentsWindow/#choose-where-an-agent-makes-changes)。

## 3. 准备和委派 {#3-prepare-and-delegate}

　　从同一已知良好提交开始两个任务，以便对照相同基线审查每个结果。

1. 在主工作区中提交两个任务都需要的更改。提交或储藏无关工作，包括要保留的未跟踪文件。确认工作树干净：

    ```shell
    git status --short
    ```

    没有输出表示没有需要处理的已跟踪或未跟踪更改。忽略文件不包括在内。

2. 运行两个任务区域的现有测试。开始前解决基线失败。

3. 在主编辑器工作区中，检出两个任务要开始的 branch。从命令面板运行 **Git: Create Branch**，输入 `integrate-agent-tasks` 或其他未使用分支名。这会为组合更改创建并检出 branch。

    将此整合 branch 作为两个工作树会话的基础。**合并更改** 操作会将每个会话合并回其配置的基础 branch，而不是稍后选择的任意目标。

4. 记录整合 branch 名称和起始提交：

    ```shell
    git branch --show-current
    git rev-parse HEAD
    ```

    在主工作区中保持整合 branch 检出。进入整合步骤之前不要向其添加更改。

5. 从标题栏的 **在智能体中打开** 按钮打开智能体窗口。选择 **新建**，选择本地项目文件夹，并选择 **Copilot** 作为 **会话目标**。

6. 选择 **新工作树**，选择记录的整合 branch 作为基础 branch。

7. 根据任务 A 的简介填写以下提示词模板并提交。将每个尖括号占位符替换为任务细节和仓库命令。依赖设置请使用项目针对新检出的正常流程。

    ```text
    Implement <task-name>.
    Outcome: <expected-outcome>

    Limit edits to <allowed-implementation-and-test-files>.
    Acceptance criteria: <acceptance-criteria>
    Preserve this existing behavior: <behavior-to-preserve>
    Out of scope: <files-and-changes-to-avoid>
    Add or update tests for the acceptance criteria.
    If the task requires edits outside this scope, stop and explain the dependency.

    Use <dependency-setup-command> if this worktree needs dependencies, then run <validation-commands>.
    Do not commit, merge, push, deploy, or modify external services.
    Finish with the changed files, validation commands and results, any manual checks still needed, and unresolved concerns.
    ```

8. 再次选择 **新建** 为同一项目创建单独会话。选择相同运行框架和整合 branch 作为基础，再次选择 **新工作树**。不要向第一个会话添加聊天。

9. 根据任务 B 的简介填写第二份模板并提交到新会话。使用任务 B 的结果、范围和验证命令，而不是任务 A 的。保持相同基础提交。

　　工作树不包含主工作区中未提交的更改。Git 忽略的文件（例如已安装依赖和本地配置）也默认缺失。请在每个工作树中使用项目正常设置流程，只提供智能体可安全访问的配置。不要复制生产凭据。详细了解[创建工作时包含文件](../../../source-control/4.5-BranchesWorktrees/#include-files-when-creating-a-worktree)。

**检查设置：** 确认两个会话报告不同工作树路径和 branch，但相同起始提交。在主工作区运行 `git worktree list` 检查路径和 branch。如果两个任务使用同一目录，请停止并更正隔离后再继续。

## 4. 监控两个任务 {#4-monitor-both-tasks}

　　使用会话列表跟踪每个任务状态。选择会话检查其对话和 **更改** 视图。发送反馈或打开终端之前，确认哪个会话处于活动状态。

> **提示**：可以在智能体窗口中并排查看多个会话，便于比较进度和更改。按需拖动排列会话。

每个任务第一次有意义的更改后检查：

* 它是否只编辑已同意文件？
* 它是否遵循验收标准？
* 它是否在等待你的回答、必要确认或正在运行的命令？
* 设置或测试是否在智能体验证更改前失败？

　　如果任务开始更改简介之外的文件，请向该任务会话发送有针对性的更正。将占位符替换为具体边界和所需证据：

```text
保持 <out-of-scope-files-or-behavior> 不变。停止扩大范围。
解释为什么 <allowed-files> 不足以实现 <expected-outcome>，并在编辑更多文件前等待我的决定。
```

　　如果任一任务发现共享依赖，请暂停受影响工作。决定先完成该依赖，还是将共享更改分配给一个任务，然后运行依赖工作。

　　单独工作树仍可能共享端口、数据库和其他外部资源。请使用单独测试资源，或一次运行一个检查。对于偏离方向或反复失败的智能体，请遵循[让智能体回到正轨](../2.6.9-GetBackOnTrack/)。

## 5. 分别审查每个结果 {#5-review-each-result-separately}

　　完成的响应是供审查的交接，不是任务正确的证明。组合之前分别审查任务 A 和任务 B。

1. 选择任务会话并打开 **更改**。检查完整 branch 差异，包括添加的测试和新文件，而不仅是最新响应。
2. 将更改与任务简介比较。检查每个验收标准是否满足、所需现有行为是否保留，以及是否有无关编辑。
3. 检查测试输出。验证预期测试已运行，设置失败或跳过测试没有被报告为成功。
4. 在该会话的工作树中运行验证命令并完成简介中的手动检查。使用会话标题栏中的 **打开终端**，运行命令前确认工作目录。
5. 将修订发送到同一会话，然后审查修订差异并重新运行受影响检查。
6. 结果准备好后，在工作树中检查 `git status --short`，查找意外或未跟踪文件。在选择 **提交更改**（会提交所有当前更改到会话 branch）之前，单独保留无关工作。
7. 记录会话 branch 名称和提交。保持会话可用，直到整合验证完成。

　　检查测试中的预期结果，而不只是测试是否通过。断言应证明任务简介中的结果，而不是重复实现中的假设。

　　完整差异和反馈流程请参阅[审查智能体更改](../../work-with-ai/2.2.8-ReviewAndRevertChanges/#choose-your-review-approach)。

## 6. 整合并重新测试 {#6-integrate-and-retest}

　　使用智能体窗口中的 **合并更改** 将每个已审查会话 branch 合并到主工作区的整合 branch。保持任务提交分开，以便在组合历史中识别每个结果。

> **注意**：**合并更改** 适用于有更改且会话 branch 没有关联拉取请求的工作树会话。它会在合并前提交任何未提交的工作树更改。请先审查所有更改，即使已经提交任务结果。如果会话 branch 有拉取请求，请使用该拉取请求的审查和合并工作流。

　　如果任一合并失败，请先遵循[恢复步骤](#if-a-merge-fails)再继续。

1. 确认两个会话已停止编辑、两个结果已提交，并且主工作树干净。
2. 在主编辑器工作区中确认整合 branch 已检出。**合并更改** 要求父仓库位于会话配置的基础 branch。如果切换过 branch，请先切回。
3. 在智能体窗口中选择任务 A 的会话。打开 **更改**，选择 **分支更改**。
4. 选择 **合并更改** 并确认。等待合并完成后再继续。
5. 返回主工作区，在整合 branch 上运行任务 A 的验证命令。如果失败，请解决并提交修复后再添加任务 B。再次确认工作树干净。
6. 在智能体窗口中选择任务 B 的会话。打开 **更改**，选择 **分支更改**，选择 **合并更改**。确认并等待合并完成。
7. 在主工作区中，对照记录的起始提交审查组合差异。确认两个已审查更改都存在，冲突解决没有移除任一任务的行为或测试。
8. 在组合 branch 上运行两个目标测试集和项目相关集成检查。包括项目贡献工作流要求的构建、类型检查或 lint 检查。
9. 从目标工作区执行两个已更改行为，使用任务简介中的手动检查：

    * 在任务 B 更改存在时确认任务 A 的预期结果。
    * 在任务 A 更改存在时确认任务 B 的预期结果。
    * 检查两个简介要求保留的现有行为。

　　每个工作树中的测试通过不能证明组合更改有效。如果整合引入失败，请在同时包含两个更改的目标 branch 上调查。提交后续修复并重新运行受影响检查。

### 如果合并失败 {#if-a-merge-fails}

　　重试之前先阅读错误。如果主工作区有未提交更改或检出了错误 branch，请先更正状态。

　　如果 Git 报告冲突，请打开主工作区，检查两个版本并保留两个任务的要求。不要为了消除冲突而整体接受一方。[解决冲突](../../../source-control/4.6-MergeConflicts/)并完成该合并，然后再运行测试或开始下一次合并。合并失败可能已经提交会话工作，即使整合未完成。

　　如果希望手动合并，请在主编辑器工作区使用 **Git: Merge Branch**，或在终端运行 `git merge --no-ff <session-branch>`，并确保整合 branch 已检出。使用实际已审查的会话 branch 名称，一次整合一个任务，并遵循相同验证步骤。不要通过另一个整合操作重复应用更改。

## 7. 完成工作流 {#7-finish-the-workflow}

　　将会话标记为完成之前，请确认：

* 每个任务都在已同意范围内，或你明确批准了范围更改。
* 分别审查并提交了每个结果。
* 两个结果都存在于预期目标 branch。
* 组合测试和手动检查通过。
* 任何整合修复都已提交。

　　继续团队正常的拉取请求或审查流程。只有之后才将会话标记为完成。工作树仍包含未保留工作时，不要删除会话或工作树。

　　现在你有一个经过测试的更改，由两个独立审查的任务组合而成，并保留每个任务的历史。
