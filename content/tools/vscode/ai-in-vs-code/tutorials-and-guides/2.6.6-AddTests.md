# 2.6.6 添加测试

　　向现有项目添加测试不仅仅是生成测试代码。需要确定哪些行为重要、遵循项目约定，并验证断言能捕获错误结果。

　　本指南介绍如何使用 VS Code 中的智能体为现有代码添加测试、运行测试、调查失败并审查结果。从一个函数或模块开始，验证第一批测试后再扩展覆盖。

　　演练使用聊天视图中的 Copilot 运行框架，在当前工作区中围绕代码协作。要将此方式与在智能体窗口中分配更高层任务比较，请参阅[选择工作方式](../../#choose-how-you-work)。

## 前提条件 {#prerequisites}

* [设置 GitHub Copilot](../../getting-started/2.1.2-SetUpCopilot/)。
* 在 VS Code 中打开现有项目。
* 安装项目依赖项和运行测试所需的运行时。

　　测试扩展对于在终端运行测试是可选的。要在测试资源管理器中发现和运行测试，请安装适当的[测试扩展](../../../debugging-and-testing/6.4-Testing/#extensions-for-testing)。

## 识别测试设置 {#identify-the-testing-setup}

　　复用项目框架和测试约定，而不是引入新的测试运行器。这有助于新测试与现有测试命令配合，并避免维护第二套设置。

1. 打开聊天视图（`Ctrl + Alt + I`，macOS：`Ctrl + Cmd + I`），开始新聊天，选择 **Copilot** 作为 **会话目标**，从智能体选择器选择 **智能体**。
2. 要求智能体在更改前检查项目：

    ```text
    检查此项目的测试设置。确定测试框架、测试应放在哪里，以及运行单个测试文件和相关测试套件的命令。
    找一个现有测试，展示项目的命名、断言和模拟约定。不要编辑文件或安装依赖。
    ```

3. 审查识别出的命令，要求智能体运行相关现有测试作为基线。记录任何失败，以便区分新测试引入的失败。

　　如果项目没有测试，请要求智能体先提出框架和最小设置。审查建议后，再要求安装依赖或更改配置。

> **提示**：要跨会话复用测试约定和防护措施，请参阅[使工作流可重复](#make-the-workflow-repeatable)。

## 定义要测试的行为 {#define-the-behavior-to-test}

　　选择小范围并描述其预期行为。聚焦的测试集更容易审查缺失情况和错误假设。将源文件和代表性现有测试作为[提示词上下文](../../work-with-ai/2.2.7-AddPromptContext/)包含，以便智能体遵循项目模式。

　　使用需求或文档化行为定义预期结果。要求智能体从实现推断所有预期，可能会生成保留现有错误的测试。

例如，如果项目有用户名验证器及以下需求，请将提示词调整为相应函数和文件名：

```text
为 `validateUsername` 提出单元测试，暂时不要编辑文件。需求是：
* 接受包含 3 到 20 个 ASCII 字母、数字或下划线的名称。
* 拒绝超出该长度范围的名称。
* 拒绝空格和其他字符。

包含有效示例、两个长度边界和无效输入。将提议用例与现有测试比较并找出缺失覆盖。
标记任何需要澄清的行为。
```

　　生成代码之前审查提议用例。对于此示例，有用的边界情况包括长度 2、3、20 和 21。在限制值和刚好超出限制处测试有助于发现差一错误。如果契约未规定 `null` 等输入的行为，请单独决定，以免智能体发明需求。

## 添加测试而不更改实现代码 {#add-tests-without-changing-implementation-code}

　　保持实现代码不变可以让测试暴露现有错误，并将修复单独审查。同意用例后，要求智能体**只**实现测试：

```text
使用现有框架和测试约定添加已同意测试。适当复用现有测试辅助函数。
不要更改实现代码、添加依赖或重构无关测试。
明确写出预期结果，不要用被测函数计算它们。
```

　　检查生成的测试。确认它们调用目标代码并断言可观察结果，而不仅是检查执行完成。保持预期结果独立于被测函数：如果测试使用该函数计算预期值，同一错误可能影响两个值并让测试通过。

## 运行测试并调查失败 {#run-tests-and-investigate-failures}

　　从覆盖更改的最小测试选择开始，以获得更快反馈并更容易隔离失败。要求智能体：

```text
使用项目现有测试命令运行新测试。报告命令、通过和失败数量以及任何跳过测试。
如果测试失败，解释原因是测试设置、错误预期还是可能的实现错误。
不要更改实现代码或弱化断言来让测试通过。
```

　　智能体可以使用可用[工具](../../work-with-ai/plan-and-run-tasks/2.2.10.2-UseTools/)运行测试并检查输出。批准执行前审查命令。如果执行被阻止或所需环境不可用，请自行运行命令并提供失败输出。将未运行的测试视为未验证。

　　接受修复之前先确定原因。失败测试可能揭示错误，也可能反映错误的测试设置或预期：

* **测试设置问题**：更正导入、夹具或配置，然后重新运行测试。
* **错误预期**：更改断言之前，将断言与已同意需求比较。
* **实现错误**：保留暴露缺陷的测试，并决定是否作为单独步骤修复实现。

　　不要仅为了获得通过结果而接受删除断言、跳过测试或更改预期值。目标测试通过后，运行相关测试套件检查与现有测试的交互。

### 使用测试资源管理器帮助 {#use-test-explorer-assistance}

　　如果测试扩展在测试资源管理器中暴露失败测试，请将鼠标悬停在失败测试上，选择 **修复测试失败**（闪光图标）请求 Copilot 帮助。接受建议更改之前，对照预期行为审查，然后重新运行测试。

## 审查断言和覆盖率 {#review-assertions-and-coverage}

　　保留更改之前，[审查差异](../../work-with-ai/2.2.8-ReviewAndRevertChanges/)和测试输出：

* 确认每个断言检查已同意需求，包括相关边界和错误情况。
* 检查测试相互独立，不依赖实时服务、共享可变状态或计时，除非这些依赖是有意的。意外依赖可能使测试结果取决于执行顺序或环境。
* 验证模拟没有替换测试应执行的行为。否则，通过的测试可能只确认了模拟配置的响应。
* 确认实现代码和无关文件保持不变。
* 检查实际执行结果，包括失败和跳过测试，而不仅依赖智能体总结。

　　如果运行器支持[测试覆盖率](../../../debugging-and-testing/6.4-Testing/#test-coverage)，请用它查找未测试分支，并决定下一步覆盖哪些行为。覆盖率显示哪些代码执行，而不是断言是否正确。通过的测试套件即使覆盖率高，也不能证明实现正确。

## 使工作流可重复 {#make-the-workflow-repeatable}

　　将测试命令、框架、模拟约定和测试质量防护措施保存到项目[自定义指令](../../customize-and-extend/2.4.4-Instructions/)。这有助于智能体跨会话遵循相同指导，而无需在每个提示词中重复。将指令纳入版本控制，与团队共享。

除了项目约定，还包含以下防护措施：

```markdown
* 不要仅为了让失败测试通过而删除或弱化断言、跳过测试或更改预期值。
* 如果断言看起来不正确，请解释原因并在更改前请求确认。
* 更改后运行相关测试。报告失败、跳过和无法运行的测试。
```

　　自定义指令引导智能体，但不强制执行这些防护措施。即使有指令，也要审查差异和测试结果。
