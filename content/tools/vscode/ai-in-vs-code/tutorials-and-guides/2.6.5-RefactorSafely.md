# 2.6.5 安全重构

　　重构会改变代码组织方式，而不改变其功能。智能体可以帮助查找重复逻辑、提出更小的结构并更新调用方，但差异看起来更整洁并不能证明行为得到保留。

　　本指南在自己的仓库中定义有界重构、建立回归覆盖、以可审查步骤进行更改，并验证现有调用方仍然工作。示例将重复的查询验证提取到共享辅助函数。

　　对于符号重命名或受支持的方法提取，请优先使用编辑器的[语言感知重构操作](../../../editor/3.2-WriteCode/3.2.6-Refactoring/)。当任务还需要调查、设计决策或这些操作无法覆盖的协调编辑时，请使用智能体。

## 前提条件 {#prerequisites}

* [设置 GitHub Copilot](../../getting-started/2.1.2-SetUpCopilot/)。
* 打开具有可用开发环境的受信任仓库。
* 确定要改进的小区域和具体目标，例如在保留 API 响应的同时移除重复验证。
* 保留无关工作，并为重构创建[开发分支](../../../source-control/4.5-BranchesWorktrees/)。

　　在该分支的当前文件夹中工作。如果现有行为不清晰，请在更改结构之前[沿代码库跟踪它](../2.6.2-ExploreACodebase/)。

## 1. 定义必须保持不变的内容 {#1-define-what-must-stay-the-same}

　　记录调用方依赖的行为：

* 接受的输入、默认值和验证边界。
* 返回值、响应结构和顺序。
* 作为契约一部分的错误类型、状态码和消息。
* 副作用，例如状态更改或外部调用。
* 其他代码使用的公共名称和接口。

　　对于示例，目标是将重复的分页验证提取到辅助函数，而不更改页码默认值、接受值、错误响应或验证顺序。排除新的 API 行为和无关清理。

1. 打开[聊天视图](../../work-with-ai/2.2.2-ChatView/)，开始新聊天。
2. 从 **会话目标** 控件选择 **Copilot**，选择 **智能体** 角色。保持 **手动审批** 选中。
3. 要求智能体调查提议的重构。将占位符替换为相关文件或符号：

    ```text
    调查 <files-or-symbols> 中重复的分页验证。比较实现并识别所有已知调用方。
    在提出共享辅助函数之前，报告默认值、接受输入、错误行为和副作用方面的差异。

    引用相关代码和测试。指出无法验证的调用方或行为。不要编辑文件或运行项目代码。
    ```

　　决定合并代码之前，先审查差异。相似函数可能有意具有不同契约。不要仅仅为了消除重复就让它们行为完全相同。

## 2. 建立回归覆盖 {#2-establish-regression-coverage}

　　要求智能体识别现有测试命令，并在你审查命令后运行相关测试。在任何实现更改之前记录结果。

　　如果行为覆盖不足，请先[为现有代码添加测试](../2.6.6-AddTests/)：

```text
为我们同意保留的行为添加回归测试。覆盖默认值、有效值、边界和无效输入，
以及每个受影响调用方的可观察结果。

使用现有测试框架。保持实现代码不变，并明确写出预期结果。
运行新测试和相关现有测试，然后报告实际结果。
```

　　对照需求和文档化行为审查断言，而不仅是对照当前实现。如果发现可能的错误，请决定是否将其作为单独更改修复。不要悄悄将重构变成行为更改，或把已知缺陷编码为预期契约。

　　将仅测试差异与实现重构分开审查。在 Git 中保留此已验证基线，以便之后比较或恢复更改。

## 3. 选择有界计划 {#3-choose-a-bounded-plan}

　　要求实现目标的最小结构：

```text
提出将已同意的验证提取到共享辅助函数的计划。列出要更新的文件和调用方，
并确定验证每一步的测试。保留我们记录的契约。

如果现有辅助函数已解决问题，请复用它们。不要添加依赖、重新设计公共接口
或重新格式化无关代码。编辑前等待我的批准。
```

　　检查计划是否涵盖每个已知调用方，并解释必须保留的任何行为差异。要求智能体将独立清理与必需重构分开。

　　提示词引导智能体，但不强制执行访问限制。实现前请审查会话的[权限和工具审批](../../work-with-ai/permissions-and-security/2.2.12.1-ApprovalsAndPermissions/)。

## 4. 以可审查步骤重构 {#4-refactor-in-reviewable-steps}

　　批准计划后，从一个小步骤开始：

```text
实现第一个已批准步骤并运行其目标测试。保留基线断言和公共行为。
此步骤完成后停止，以便我在更新其余调用方之前审查差异。
报告任何意外行为或需要的计划更改。
```

　　检查差异和测试输出。只有在当前步骤已理解并验证后，才继续下一步。

　　保留通过现有公共入口点验证行为的测试。为辅助函数新增单元测试有用，但不能替代原始调用方仍然工作的证据。

　　如果测试依赖重构会移除的私有实现细节，请单独审查必要的测试更新。保留可观察预期，而不是自动重写测试以匹配新代码。

## 5. 检查调用方和兼容性 {#5-check-callers-and-compatibility}

计划编辑完成后：

1. 检查对已更改符号的所有引用。检查导入、导出、配置引用以及编辑文件之外的调用方。
2. 运行目标测试和相关测试套件，包括每个受影响调用方的测试。
3. 运行项目适用的构建、类型检查和 lint 检查。
4. 通过原始入口点执行有代表性的有效和无效输入。
5. 将结果与记录的基线比较，包括错误和副作用。

　　源引用和通过的测试不能证明外部使用方兼容。如果影响已发布 API、包导出或持久化格式，请对照相关使用方契约验证。无法建立所需兼容性时，请推迟更改。

　　将未执行的检查视为未验证。要求智能体报告环境故障或缺失测试资源，而不是声称完成。

## 6. 审查并保留重构 {#6-review-and-keep-the-refactor}

　　[审查完整差异](../../work-with-ai/2.2.8-ReviewAndRevertChanges/)，对照目标和保留行为。检查无关格式、依赖更改、弱化测试或默认值和错误处理的意外更改。

　　要求简洁总结结构更改、已检查调用方、已运行测试和剩余不确定性。提交预期更改之前，对照差异和命令输出验证总结。

　　如果行为意外改变，请停止并调查。使用版本控制基线或[智能体恢复工作流](../2.6.9-GetBackOnTrack/)恢复不需要的编辑，而不丢弃无关工作。

　　最终你会得到更小或更清晰的实现，以及证明要保留的行为仍然成立的证据。
