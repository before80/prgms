# 2.6.3 添加功能

　　添加功能不仅仅是生成新代码。更改需要符合项目结构、保留现有行为，并有证据证明其正常工作。

　　本指南在自己的仓库中使用智能体研究一个小功能、审查计划、实现更改并为拉取请求准备已验证结果。不需要先创建自定义智能体或指令。

　　示例为分页议题 API 添加可选的标题筛选器。请将提示词和验收标准调整为项目中的功能。不需要特定框架或示例项目。

## 前提条件 {#prerequisites}

* [设置 GitHub Copilot](../../getting-started/2.1.2-SetUpCopilot/)。
* 打开具有可用开发环境和现有测试的受信任仓库。
* 选择具有可观察结果的小功能。如果不熟悉实现，请先[探索代码库](../2.6.2-ExploreACodebase/)。
* 保留无关工作，并使用团队正常工作流创建[开发分支](../../../source-control/4.5-BranchesWorktrees/)。

　　对于本指南，请在该分支的当前文件夹中工作。让智能体在现有项目中工作之前，请审查[推荐的安全基线](../../work-with-ai/permissions-and-security/2.2.12.3-AISecurity/#recommended-security-baseline)。

## 1. 定义功能 {#1-define-the-feature}

　　描述应更改什么、必须保持不变什么以及如何检查结果。避免“添加搜索”之类将重要行为留给智能体自行发明的请求。

对于示例 API，功能简介如下：

| 要求 | 预期行为 |
|---|---|
| 可选筛选 | `GET /issues?q=<text>` 返回标题包含文本的议题，忽略大小写。 |
| 空筛选 | 缺少、为空或仅空白的 `q` 保留未筛选结果。去除首尾空白。 |
| 分页 | 筛选发生在分页之前。现有 `total` 字段统计所有匹配议题，而不仅是当前页。 |
| 无匹配 | 返回现有响应结构，议题列表为空，`total` 为零。 |
| 兼容性 | 保留现有排序、页码、页大小、验证和响应字段。 |
| 范围 | 复用当前 API 和测试框架。不要添加 UI、依赖项或新搜索服务。 |

　　使用提示词之前，请检查这些假设是否与 API 匹配。例如，如果 API 没有 `total` 字段，请决定客户端应如何确定结果数量，而不是无意中添加字段。

## 2. 建立基线 {#2-establish-the-baseline}

1. 打开[聊天视图](../../work-with-ai/2.2.2-ChatView/)，开始新聊天。
2. 从 **会话目标** 控件选择 **Copilot**，选择 **智能体** 角色。保持 **手动审批** 选中。
3. 要求智能体检查实现和测试约定，但不要编辑：

    ```text
    查找议题列表终结点、其分页逻辑和相关测试。找出一个现有可选查询参数作为模式（如果存在）。
    报告运行目标测试和相关测试套件的相关文件和命令。
    现在不要编辑文件、安装依赖或运行命令。
    ```

4. 审查识别出的文件和命令。要求智能体运行受影响区域的现有测试，并检查实际输出。

　　继续之前，解决阻止验证功能的失败。将无关的基线失败单独记录，以免与更改引入的回归混淆。

## 3. 编辑前审查计划 {#3-review-a-plan-before-editing}

　　提供已同意的功能简介并要求计划：

```text
规划功能简介中的可选标题筛选器。确定要更改的实现和测试文件、要复用的现有辅助函数
以及需要更新的 API 文档。

包含针对缺失、空和仅空白筛选器、去除空白、混合大小写匹配、无匹配以及分页前筛选的测试。
保留现有响应结构、排序和分页行为。

确定未解决决策和兼容性风险。不要编辑文件。等待我的批准后再实现。
```

　　也可以使用专门的[规划工作流](../../work-with-ai/plan-and-run-tasks/2.2.10.1-PlanWork/)创建和完善计划。等待批准的指令不会更改会话工具权限。

　　审查计划是否遵循你检查的代码。它应命名实际文件、考虑现有客户端，并解释测试如何证明验收标准。批准之前解决歧义。

　　例如，检查分页测试是否使用足够多的匹配记录跨越多个页面。只有一条匹配记录的测试可能无法发现分页之后才进行筛选的问题。

## 4. 实现已批准的更改 {#4-implement-the-approved-change}

　　要求智能体仅实现已同意范围：

```text
使用此项目现有模式实现已批准计划。为已同意的验收标准添加测试并更新 API 文档。
不要添加依赖或重构无关代码。

运行目标测试，然后运行相关测试套件。报告命令、通过和失败数量以及任何跳过或无法运行的检查。
如果计划需要更改，请解释原因并等待我的决定。
```

　　智能体工作时审查工具请求和正在更改的文件。如果它发现共享依赖或提议更广泛的 API 更改，请重新审查计划，而不是让范围隐性扩大。

　　如果智能体更改无关行为，请发送有针对性的更正。对于反复失败或不想要的更改，请使用[智能体恢复指南](../2.6.9-GetBackOnTrack/)。

## 5. 验证功能和现有行为 {#5-verify-the-feature-and-existing-behavior}

　　完成消息不能证明功能有效。检查测试及其输出，然后亲自执行行为。

对于示例 API：

1. 使用具有混合大小写标题、不匹配标题和足够跨多页匹配的已知测试数据。
2. 将不带 `q` 的请求与基线比较。现有客户端应收到相同行为。
3. 对照已同意规则检查空、仅空白和带首尾空白的筛选值。
4. 请求筛选结果的每一页。验证预期议题 ID、排序、总数，并且没有缺口或重复。
5. 检查无匹配筛选，确认响应结构未变。
6. 重复现有无效页码检查，确认功能没有削弱验证。

　　按需运行项目必需的构建、类型检查或 lint 检查。如果无法运行检查，请记录原因并在所需环境中安排验证，然后才能视为完成。

　　测试失败时，在更改测试或实现之前，先将结果与功能简介比较。不要仅仅为了获得通过结果而接受弱化断言或跳过的测试。

## 6. 为审查准备更改 {#6-prepare-the-change-for-review}

　　[审查完整差异](../../work-with-ai/2.2.8-ReviewAndRevertChanges/)，包括测试、文档和未跟踪文件。确认每项更改都支持已批准功能，且没有包含无关工作。

要求智能体提供审查总结：

```text
为拉取请求总结此更改。解释用户可见行为、如何保持兼容性以及执行的验证。
列出未运行的检查和剩余限制。总结应基于实际差异和命令输出，而不仅是计划。
不要提交或发布任何内容。
```

　　审查总结，提交预期更改，并通过团队正常流程打开拉取请求。使用相同范围和验收标准处理审查反馈，然后重新运行受影响检查。

　　现在你拥有一个功能，其实现、测试和审查总结可以与明确要求集比较。
